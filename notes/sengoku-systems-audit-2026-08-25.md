# Audit ระบบเนื้อหาเซนโกคุ: ไทม์ไลน์ แผนที่ การเดินเรือ และ AI GM

> **ขอบเขต:** เอกสารนี้ตรวจจากโค้ดและเอกสารที่มีอยู่แล้วใน repository เท่านั้น ไม่มีการทำวิจัยใหม่หรือแทนที่ฐานงานวิจัยเดิม

## ภาพรวมสถานะ

Dust & Fire มีฐานสำหรับวางเรื่องในญี่ปุ่นยุคเซนโกคุแล้วในสามชั้น ได้แก่ **บริบทประวัติศาสตร์ที่มีแหล่งอ้างอิง**, **แผนที่ระดับประเทศเพื่อวางตำแหน่งแคมเปญ**, และ **AI GM ที่เลือก fact card ตามบริบทฉาก** ระบบทั้งสามตั้งใจแยกประวัติศาสตร์ออกจากผลทอยและ fiction ของแคมเปญอย่างชัดเจน แต่ยังไม่มีระบบเดินเรือ, เส้นทาง, หรือไทม์ไลน์รายปีที่ครอบคลุมหลายปีแบบละเอียด

| พื้นผิว | สถานะ | สิ่งที่มีอยู่จริง | ขอบเขตที่ตั้งใจไว้ |
|---|---|---|---|
| ไทม์ไลน์ประวัติศาสตร์ | มีฐานเริ่มต้น | 7 รายการที่ผ่านการตรวจ, ครอบคลุมปี 1569–1570 | Read-only; ไม่เปลี่ยน roll, mission หรือ Local Save |
| แผนที่ระดับประเทศ | ใช้งานได้ | 68 province hotspots บนแผนที่ national context | ไม่ใช่แผนที่ดินแดนครอบครอง และไม่ใช่เส้นทางเดินทาง |
| การเดินเรือ | ยังไม่มีระบบ | บริบทเมืองท่า/ทะเลใน prose และ fact card maritime | ไม่มีเรือ, ท่าเรือ, ลูกเรือ, route, เวลาเดินทาง หรือ simulation |
| AI GM ความรู้เซนโกคุ | มีรั้วคุณภาพ | 12 fact cards ครอบคลุม 10 domains พร้อม source IDs | ใช้ตามปี/ภูมิภาค/ความมั่นใจ และห้ามแต่งเป็นข้อเท็จจริง |
| เนื้อหา player-facing | รีเซิทแล้ว | Narrative Style Contract, Story Records, Relationships แบบไม่สปอยล์ | กลไกทอยและข้อมูล NPC ลับไม่ปนกับ prose ที่ผู้เล่นอ่าน |

## สิ่งที่รีเซิทหรือพัฒนาแล้วในเนื้อหา

การรีเซิทที่ผ่านมาไม่ได้ลบ Character Sheet หรือเรื่องเดิมออก แต่เปลี่ยน **มาตรฐานคุณภาพและเส้นแบ่งข้อมูล** ให้ชัดขึ้น งานเขียนทั้งไทยและอังกฤษถูกกำกับด้วย Narrative Style Contract v2 เพื่อกันศัพท์เกม, modernism, faux-archaic English และการเล่ารู้เกินมุมมองผู้เล่น ขณะเดียวกัน AI GM ต้องรักษามารยาทตามสถานะ, วิถีชีวิต, ความกดดันจากฤดูกาล, การค้า, เอกสาร และผู้คนในฉาก ตาม fact card ที่เข้าเงื่อนไข

| ส่วนเนื้อหา | สิ่งที่เปลี่ยน | ผลต่อผู้เล่น |
|---|---|---|
| ร้อยแก้ว Play Scene | local fallback และ AI output ถูกตรวจคุณภาพก่อนปล่อย | อ่านเป็นฉาก ไม่ใช่รายงานผลทอย |
| บทสนทนา TH/EN | แยก register ตามระยะห่าง/ฐานะ; ห้ามไทยราชาศัพท์เกินจริงและห้าม English โบราณปลอม | เสียงตัวละครเป็นธรรมชาติขึ้นทั้งสองภาษา |
| Story Records | หนึ่ง record ต่อ Play Scene ที่จบแล้ว; เก็บชื่อฉาก, วันในเกม, สถานที่, ร้อยแก้วเต็ม | กลับมาอ่านเรื่องตามลำดับได้ โดยไม่เห็น dice, DN, skill หรือ progress |
| Relationships | ใช้ public projection, evidence และ daily pending log; dossier ลึกอยู่ server only | เห็นเท่าที่ตัวละครรู้ ไม่ถูกสปอยล์เจตนาภายใน NPC |
| Historical Fence | ป้าย `fact-supported`, `contextual-play`, `campaign-fiction`, `insufficient-evidence` | แยกชัดว่าอะไรเป็นประวัติศาสตร์และอะไรเป็น fiction ของแคมเปญ |

## ไทม์ไลน์ประวัติศาสตร์: มีอะไรใน repository แล้ว

Catalog ปัจจุบันเป็นชุดข้อมูลแบบ source-controlled มี field สำหรับ `kind`, `year`, `date precision`, `season`, `month`, ข้อความสองภาษา, `regionKeys` และ source URL จึงวางโครงสำหรับไทม์ไลน์รายปีที่ละเอียดได้แล้ว อย่างไรก็ดี **เนื้อหาจริงมีเพียง 7 รายการใน 2 ปี**: ปี 1569 มี 2 รายการ และปี 1570 มี 5 รายการ ไม่ใช่ chronology ครบทุกปีของยุคเซนโกคุ

| ปี | จำนวน | ตัวอย่างที่มี | ระดับวันที่ | ข้อสังเกต |
|---:|---:|---|---|---|
| 1569 | 2 | Honkoku-ji Incident; การสร้างตำหนักนิโจ | ระดับปี | ไม่มี record ที่ตรง Izumi/Sakai โดยตรง |
| 1570 | 5 | Kanegasaki, Anegawa, Ishiyama War, Noda–Fukushima, Siege of Shiga | เดือน/ฤดู/วันจริงผสมกัน | มี Omi และ Settsu; relevance คำนวณตามจังหวัด |

> ระบบไม่เติมปีที่ยังไม่มีข้อมูลด้วยเรื่องแต่ง: UI จะแสดงว่าปีนั้นยังไม่มี reviewed record แทนการทำให้ดูเหมือนประวัติศาสตร์ครบแล้ว

### แผนรีเซิทไทม์ไลน์ที่ควรทำต่อ

การรีเซิทที่ถูกต้องคือ **ขยาย catalog อย่างมีรั้ว** ไม่ใช่ rewrite ใส่ทุกเหตุการณ์หรือทำแผนที่ยึดครองแบบเดาเอง ขั้นแรกควรยืนยัน supported campaign windows ก่อน จากนั้นจึงเพิ่ม record ต่อปีด้วย date precision ที่ซื่อตรงกับแหล่งข้อมูล และ tag relevance ให้แคมเปญแสดงเฉพาะบริบทที่เกี่ยวข้อง

| ลำดับ | สิ่งที่เพิ่ม | สิ่งที่ต้องคงไว้ |
|---:|---|---|
| 1 | Scope ปีและภูมิภาคที่เกมจะสนับสนุนจริง | ปีที่ยังไม่มี source ต้องแสดง incomplete |
| 2 | Annual index ต่อปี → season/month/exact-date เท่าที่หลักฐานให้ | ห้ามสร้างฤดูหรือวันที่เทียม |
| 3 | `regionKeys`, kind battle/event, source ID และ Historical Fence | Timeline ห้าม mutate game state |
| 4 | Timeline reader แบบปีต่อปีและ filter จังหวัด | แยก national context ออกจาก quest เนื้อเรื่อง |
| 5 | Editorial review status ต่อ record | NPC และผลของผู้เล่นยังเป็น campaign fiction |

## แผนที่ปัจจุบัน: มี 68 จุดจังหวัด แต่ไม่ใช่ระบบเส้นทาง

National Context Map ใช้ artwork ที่ได้รับอนุญาตสำหรับตำแหน่งกว้าง และวาง hotspot ชื่อจังหวัดด้วยพิกัดโดยประมาณ ผู้เล่นดูตำแหน่งปัจจุบัน, ซูมดูจังหวัด, และเปิด province brief ได้ Map ไม่แสดง polygon เขตครอบครองหรืออ้างว่าใครคุมทุกพื้นที่ ซึ่งเป็นการตัดสินใจด้านความปลอดภัยทางประวัติศาสตร์ที่ถูกต้อง

| ความสามารถที่มี | วิธีทำงานปัจจุบัน | ช่องว่างที่ยังไม่มี |
|---|---|---|
| National orientation | marker ตำแหน่งแคมเปญบน map ระดับประเทศ | route planner จากจุด A ไป B |
| Province detail | ซูมและเลือก hotspot จังหวัดใกล้เคียง | node ของท่าเรือ, จุดขึ้นฝั่ง, แม่น้ำ, ช่องเขา |
| Local context | prose ประจำจังหวัด เช่น Izumi, Settsu, Shima, Iyo | ค่าเวลา, ระยะทาง, ลม, น้ำขึ้นลง, เสบียง |
| Timeline context | card เหตุการณ์ตาม year/region | แผนที่ layer ของเหตุการณ์หรือเส้นทางในปีนั้น |

## การเดินเรือ: ตอนนี้เป็น “บริบท” ไม่ใช่ “ระบบ”

ปัจจุบันเกมรู้คำเกี่ยวกับ `port`, `sea`, `ship`, `translator`, `ท่าเรือ`, `ทะเล`, `เรือ`, `ล่าม` เพื่อเลือก fact card ที่เกี่ยวข้อง และ prose ของ Izumi, Settsu, Shima, Iyo พูดถึงท่าเรือ, ช่องน้ำ, จุดขึ้นฝั่ง และเครือข่ายทางน้ำได้ แต่ไม่มี state หรือ rule สำหรับเรือจริง

| สิ่งที่ GM ใช้เขียนได้แล้ว | สิ่งที่ระบบยังไม่มี | ข้อเสนอเมื่อเริ่มทำในอนาคต |
|---|---|---|
| พ่อค้า, นายหน้า, ล่าม, ผู้ค้ำ, เอกสาร, ท่าเรือ, การตรวจของ | vessel, crew, cargo manifest, port authority, voyage state | Voyage dossier แบบ narrative-first แยกจาก roll engine |
| เมืองท่า/ลมทะเล/จุดขึ้นฝั่งเป็น scene pressure | route graph, ETA, tide/weather model | Port/landing nodes + เหตุการณ์การเดินทางที่มีหลักฐาน |
| การค้าใช้เงิน/ของ/เครดิตเอกสารได้หลายแบบ | ค่าระวาง, ความเสี่ยง, การรบทางเรือ | Travel consequence สร้าง story evidence ไม่บังคับผลทอย |

## AI GM “รู้อะไร” เกี่ยวกับเซนโกคุ

AI GM ไม่ได้ถูกปล่อยให้ใช้ความทรงจำกว้าง ๆ อย่างเดียว ระบบเลือก fact card สูงสุด 5 ใบจาก action และ scene โดยกรองตามช่วงปี ก่อนเรียงตาม domain ที่เกี่ยวข้อง Fact card 12 ใบครอบคลุม 10 domains: household, market, travel, faith, war, language, status, season, health และ maritime

| ความรู้ที่เลือกได้ | วิธีใช้ในการเขียน | สิ่งที่ GM ห้ามทำ |
|---|---|---|
| ตลาด/สิทธิ์/นายหน้า | ให้ค่าแก่ค่าผ่านทาง ผู้ค้ำ การตรวจ และเครือข่ายข่าว | ทำให้ทุกตลาดเสรีหรือใช้ระบบเดียวทั้งประเทศ |
| ครัวเรือน/สถานะ | เขียนหนี้ การดูแล ชื่อเสียง งาน และการคุ้มครอง | ใช้ชนชั้นสี่แบบเอโดะเป็น default เซนโกคุ |
| สงคราม/แรงงาน | แสดงผลผ่านเสบียง คนงาน ปิดทาง ภาษี และแรงกดดัน | บังคับว่าทุกคนต้องเชื่อฟังไดเมียวทันที |
| วัด/ศรัทธา/เอกสาร | วางผู้ไกล่เกลี่ย พยาน สำเนา ตรา และเจ้าของเอกสาร | ทำวัดหรืออิกโกอิกกิเป็นกลุ่มเดียวไร้ความต่าง |
| ฤดูกาล/สุขภาพ | ใช้บริบทต่อเสบียง ราคา แรงงาน การรักษาและครอบครัว | สุ่มภัยพิบัติจริงหรือวินิจฉัยโรคจริง |
| ท่าเรือ/การค้าต่างถิ่น | ให้บทบาทแก่ล่าม คนเขียน นายหน้า ศาสนา และความไว้ใจ | ใส่ของต่างชาติ/อาวุธปืนในทุกหมู่บ้าน |

AI GM ยังถูกบังคับให้ **ไม่ทอยลูกเต๋า**, ไม่เปลี่ยน resource, ไม่ตั้ง Context/Gear เกิน +2, ไม่เปลี่ยน DN, ไม่กระโดดข้าม deterministic engine และต้องปล่อย JSON ที่ผ่าน Narrative Style Contract เท่านั้น ข้อมูล private NPC dossier ไม่ถูกส่งให้ browser save หรือ UI ของผู้เล่น

## สรุปการตัดสินใจสำหรับรอบถัดไป

ระบบที่เหมาะจะทำก่อนคือการทำ **timeline catalog/editorial workflow** ให้ครบสำหรับปีและภูมิภาคที่เลือก ไม่ใช่สร้าง sea simulation ทันที แผนที่ national context มีฐานแข็งแรงสำหรับแสดง route และ port layers ภายหลัง แต่ยังควรเป็นชั้นเล่าเรื่องที่ไม่ทำลายกติกา deterministic ระบบเดินเรือควรเริ่มจาก **port/landing/route dossier แบบ evidence-driven** แล้วค่อยเพิ่ม state เมื่อมี content และ design contract ที่ตรวจแล้ว
