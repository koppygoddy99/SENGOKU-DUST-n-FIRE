## 1. เจตนารมณ์ของเกม

### 1.1 ประโยคสัญญาของเกม

ผู้เล่นพูดสิ่งที่ตัวละครทำ **เพียงหนึ่งประโยค**; ระบบเป็นผู้แบกงานหนักของการเลือกแกนทอย ความชำนาญ โบนัสจากบริบท ระดับความยาก และผลตามมา ผู้เล่นไม่จำเป็นต้องประกาศค่ากลไกก่อนทอย และไม่ควรถูกบังคับให้คิดเหมือนนักบัญชีกติกา

ผลลัพธ์ไม่ควรจบที่ “สำเร็จ” หรือ “ล้มเหลว” เท่านั้น ทุกผลควรทำให้โลกมีรอยเพิ่มขึ้นอย่างน้อยหนึ่งอย่าง เช่น คนเป็นพยาน ชื่อถูกจด หนี้เกิดขึ้น ข่าวเดินทาง ของเสียหาย ทางเปิด หรือผู้มีอำนาจเริ่มสนใจ

| หลัก | ความหมายในการเล่น | ความหมายในการพัฒนา |
|---|---|---|
| **Agency before procedure** | ผู้เล่นบอกเจตนาและวิธีการด้วยภาษาธรรมชาติ | ห้ามทำให้ผู้เล่นต้องกรอกสูตรกติกาเพื่อเล่นได้ |
| **Consequences are records** | สิ่งที่เกิดขึ้นควรตามกลับมาได้ | ผลสำคัญต้องเขียนเป็น `Memory`, `Obligation`, `ExchangeRecord`, หรือ state ที่ตรวจสอบได้ |
| **Status creates pressure, not immunity** | ยศ ชื่อเสียง หรือความชำนาญไม่ควรล้างความเสี่ยง | หลีกเลี่ยงโบนัสที่ทำลายความตึงเครียดของ 2d12 |
| **History is a boundary** | ความจริงทางประวัติศาสตร์ไม่ใช่ของตกแต่ง | ระบุชัดว่าเป็นข้อเท็จจริง บริบท เรื่องสมมติ หรือข้อมูลไม่พอ |
| **Local-first continuity** | เรื่องต้องเดินได้แม้ AI หรือหลังบ้านใช้ไม่ได้ | กติกาทอย เซฟ และ log ต้องพึ่งฝั่งท้องถิ่นได้ |

### 1.2 สิ่งที่เกมไม่ใช่

เกมนี้ไม่ใช่สารานุกรมที่สรุปยุคเซ็นโกกุเป็นบทเรียน และไม่ใช่เกมสงครามที่ลดคนให้เหลือค่าความเสียหาย เกมไม่ถือว่า “บูชิโด” เป็นกฎศีลธรรมสากลที่ทำให้ทุกคนคิดเหมือนกัน และไม่ใช้ประวัติศาสตร์เป็นใบอนุญาตให้สร้างข้อเท็จจริงเทียม

เกมมองเกียรติเป็น **แรงต่อรองของสังคม**: เกียรติอาจเปิดประตูให้คนฟังคำพูด แต่ก็ทำให้ผู้เล่นถูกผูกกับคำมั่นและพยาน ความเน่าเฟะของอำนาจจึงไม่ใช่ฉากหลังที่แยกจากการเล่น แต่เป็นสิ่งที่ควรแสดงผ่านราคาที่คนยอมจ่ายเพื่อรอด

## 2. หลักการสำหรับผู้เล่น

### 2.1 หน่วยพื้นฐานของการเล่น: การประกาศเจตนา

ผู้เล่นควรบอก **สิ่งที่ทำ**, **วิธีที่ทำ**, และถ้ามี **สิ่งที่ยอมเสี่ยง** ในประโยคเดียว ตัวอย่างเช่น

> “ข้าจะอ้างบัญชีเสบียงของหมู่บ้านต่อหน้าผู้คุม เพื่อซื้อเวลารอคนเก็บเกี่ยวกลับมา”

ประโยคนี้ให้ข้อมูลพอสำหรับระบบตีความว่าเป็นการใช้เอกสาร เหตุผล และการต่อรองต่อหน้าพยาน โดยผู้เล่นไม่ต้องระบุว่าใช้แกนปัญญา ความชำนาญบัญชี หรือ DN ใด

| เขียนแบบนี้ | เพราะอะไร |
|---|---|
| “ข้าจะหลอกผู้คุมให้เปิดประตู” | มีเป้าหมายชัด แต่ยังไม่ระบุวิธี; ระบบยังทอยได้ แต่อาจให้ความเสี่ยงกว้าง |
| “ข้าจะบอกว่าขบวนเป็นของวัดและยื่นจดหมายรับรอง เพื่อให้ผู้คุมปล่อยครอบครัวผ่าน” | บอกวิธี อุปกรณ์ และเดิมพันทางสังคม; เหมาะสำหรับฉากเชิงนิยาย |
| “ข้าจะทอยไหวพริบ +3” | ไม่ใช่ภาษาที่ผู้เล่นต้องใช้; ระบบเป็นผู้พิจารณากลไก |
| “ข้าต้องชนะ” | เป็นความต้องการ ไม่ใช่การกระทำ; ควรเพิ่มสิ่งที่ตัวละครจะทำจริง |

### 2.2 คำถามที่ควรถามก่อนลงมือ

ก่อนทอย ผู้เล่นควรคิดเพียงสี่เรื่อง ไม่จำเป็นต้องคิดสูตร

| คำถาม | ตัวอย่าง |
|---|---|
| **ข้าต้องการเปลี่ยนอะไร?** | ให้ผู้คุมปล่อยคนผ่าน, เอาเอกสารคืน, หยุดข่าวลือ |
| **ข้าทำผ่านสิ่งใด?** | คำพูด, อาวุธ, เอกสาร, ของกำนัล, คนกลาง, เส้นทาง |
| **ใครต้องจ่ายราคา?** | ตัวละคร, คนในบ้าน, ผู้ค้ำ, ชุมชน, คนที่ถูกทิ้งไว้ |
| **ใครเห็น?** | ผู้คุม, เสมียน, คนงาน, คู่แข่ง, คนในเซฟเฮาส์ |

ผู้เล่นมีสิทธิ์ล้มเหลวโดยเรื่องยังเดินต่อได้ ความพลาดที่ดีควรทำให้ทางเดิมปิดลง แล้วเปิดปัญหาใหม่ที่เล่นต่อได้ ไม่ใช่หยุดแคมเปญ

## 3. แกนกติกา 2d12

### 3.1 สูตรการทอย

กติกาท้องถิ่นใช้การทอยลูกเต๋าสิบสองหน้า 2 ลูก และรวมค่าต่อไปนี้

```text
Total = d12 + d12 + Axis + Mastery + Context Bonus + Momentum Bonus
Margin = Total − Difficulty
```

| ส่วนของผลรวม | แหล่งข้อมูล | ขอบเขตปัจจุบัน |
|---|---|---|
| **d12 + d12** | การสุ่มของกติกา | 2–24 ก่อนโบนัส |
| **Axis** | ค่าห้าแกนของตัวละคร | เริ่มจากอาชีพ; ระบบ AI รับค่า 0–6 |
| **Mastery** | ความชำนาญที่ตรงการกระทำ | ระดับ 0–3 ในข้อมูลเริ่มต้น |
| **Context Bonus** | ของใช้ได้หรือบริบทที่ตรงแท็ก | ปัจจุบันมักเป็น +1; AI GM ถูกจำกัดไม่เกิน +2 |
| **Momentum Bonus** | ใช้ Momentum หนึ่งหน่วยหลังเห็นผลทอย | +2 และลด Momentum 1 |

### 3.2 ห้าแกนการกระทำ

| ID | English | คำไทย | ใช้เมื่อ | ไม่ได้หมายความว่า |
|---|---|---|---|---|
| `body` | Prowess | **พละกำลัง** | แบก ฝ่า ยื้อ ปีน วิ่ง ต้านแรง | การต่อสู้ทุกชนิดเสมอไป |
| `hand` | Craft | **ฝีมือ** | ฟัน ยิง ซ่อม แกะ จับ ใช้อาวุธหรือเครื่องมือ | แค่มือไวโดยไร้ความรู้ |
| `wit` | Instinct | **ไหวพริบ** | หลบ ลอบ หลอก สังเกต หนี อ่านจังหวะ | สติปัญญาเชิงเอกสารหรือแผนระยะยาว |
| `mind` | Judgment | **ปัญญา** | อ่านบัญชี พิสูจน์ วางแผน อ้างเอกสาร คำนวณ | ความฉลาดเหนือทุกคนในห้อง |
| `heart` | Resolve | **พลังใจ** | ยืนหยัด ขอร้อง สาบาน รับผิด ชักจูง ปกป้อง | การบังคับใจ NPC อย่างอัตโนมัติ |

การกระทำหนึ่งอย่างอาจแตะหลายแกนได้ แต่ระบบควรเลือก **แกนที่เป็นวิธีหลัก** ของการกระทำนั้น ตัวอย่าง “ยื่นตราเพื่อขอผ่านด่าน” มักเป็นปัญญาเพราะอำนาจของเอกสารเป็นแกนหลัก; หากผู้เล่นเปลี่ยนเป็น “แบกคนเจ็บปีนกำแพง” จึงเป็นพละกำลัง

### 3.3 ความชำนาญ

ความชำนาญ (`Mastery`) ไม่ใช่รายการ skill ที่ผู้เล่นเอามาอ้างเพื่อบังคับผล แต่คือความเชี่ยวชาญที่มีต้นทางและแท็กอธิบายว่าเหตุใดตัวละครจึงน่าจะทำสิ่งนั้นได้ดีขึ้น

```ts
type Mastery = {
  id: string;
  label: string;
  level: number;
  origin: string;
  tags: string[];
}
```

ระบบ Local Trial เลือกความชำนาญที่แท็กสอดคล้องกับคำสำคัญของ action หรือวิธีที่จับคู่ไว้ ความชำนาญระดับสูงกว่าจะถูกเลือกก่อนเมื่อเงื่อนไขใกล้เคียงกัน นักพัฒนาควรรักษาแท็กให้เป็นคำที่มีความหมายเชิงการเล่น เช่น `document`, `route`, `fight`, `repair`, `negotiation` ไม่ใช่ข้อความคลุมเครือ

### 3.4 ระดับความยาก

โหมด Local Trial ใช้ระดับมาตรฐานสี่ชั้น

| Difficulty | ใช้เมื่อ | ตัวอย่าง |
|---:|---|---|
| **10** | แรงกดดันต่ำหรือคำประกาศยังสั้น/กำกวม | ถามข่าว, ขอยืมเชือก, ตรวจทางออก |
| **14** | การกระทำมีเป้าหมายและความเสี่ยงทั่วไป | ต่อรองเรื่องเล็ก, ซ่อมของ, เดินทางผ่านตลาดที่ตึงเครียด |
| **18** | เกี่ยวกับด่าน ผู้คุม ค่าย การตรวจ หรือแรงกดดันชัดเจน | ยื่นเอกสารต่อหน้าผู้คุม, ลอบผ่านจุดตรวจ |
| **22** | ฆ่า ปลอม ขโมย บุก หรือการกระทำที่เปิดความรุนแรง/ข้อครหาหนัก | ปลอมตรา, บุกคลัง, สังหารต่อหน้าพยาน |

AI GM อาจเสนอค่าระหว่าง 5–30 แต่ไคลเอนต์ต้อง canonicalize กลับเป็น 10, 14, 18 หรือ 22 เสมอ เพื่อให้กติกาหลักไม่เปลี่ยนไปตามอารมณ์ของโมเดล

### 3.5 ผลลัพธ์จาก Margin

| Margin | Outcome ID | คำอธิบาย | สิ่งที่เรื่องควรทำต่อ |
|---:|---|---|---|
| `≥ +5` | `decisive_success` | **สำเร็จเด็ดขาด** | เปิดทางใหม่และความไว้วางใจ แต่ให้ทิ้งรอยผูกมัดที่ใช้ทวงได้ภายหลัง |
| `0 ถึง +4` | `success_with_cost` | **สำเร็จ แต่มีผลตามมา** | เป้าหมายเกิดขึ้นพร้อมพยาน หนี้ ข่าว หรือสิทธิ์ที่ต้องตอบแทน |
| `−4 ถึง −1` | `partial_success` | **สำเร็จบางส่วน** | ได้บางอย่าง เช่น เวลา ข้อมูล หรือช่องทาง แต่แรงกดดันยังอยู่ |
| `≤ −5` | `failure_with_consequence` | **ไม่สำเร็จ** | ทางเดิมใช้ไม่ได้ สถานการณ์แย่ลง หรือผู้คนเริ่มสงสัย; ต้องมีทางเลือกถัดไป |

### 3.6 Momentum — แรงฮึด

Momentum เป็นทรัพยากรสำหรับยอม “ฝืน” ผลที่กำลังจะเกิด ไม่ใช่สิทธิ์ลบผลเสีย ผู้เล่นใช้ได้เมื่อมี Momentum มากกว่า 0 และเลือกใช้หลังเห็นผลทอย ระบบจะเพิ่ม +2 แล้วลด Momentum 1

> แนวออกแบบ: Momentum ควรเกิดจากความสัมพันธ์ คำสัตย์ การเตรียมตัว หรือการยอมเสียบางอย่างในเนื้อเรื่องในอนาคต ไม่ควรแจกแบบสุ่มเพื่อแก้ความโชคร้ายอย่างเดียว

## 4. ตัวละคร อาชีพ และแรงดึง

### 4.1 โครงตัวละคร

ตัวละครมีหกกลุ่มข้อมูล: ตัวตน, แกนและความชำนาญ, สถานะ, สังคม, ทรัพยากร, และแรงดึงทางความสัมพันธ์

| กลุ่ม | ตัวอย่าง | บทบาทในเกม |
|---|---|---|
| **Identity** | ชื่อ, เพศ/ตัวตน, อาชีพ, ถิ่นกำเนิด | ให้ภาษาของฉากและขอบเขตทางสังคม |
| **Strength / Weakness** | จุดเด่นและจุดด้อย | สิ่งที่การเขียนฉากและ GM ควรหยิบมาเร่งแรงกดดัน |
| **Attributes / Masteries** | ห้าแกนและความชำนาญ | ผลต่อการ resolve |
| **Vitals** | Wounds, Focus, Momentum | ความเปราะบางและทรัพยากรระหว่างฉาก |
| **Social** | Rank, Honor, Influence, Information, Stain | ร่องรอยทางสังคมที่ควรมีผลต่อการเข้าถึงและปฏิกิริยา |
| **Resources / Inventory** | Property, Supplies, Credit และของ | สิ่งที่ใช้จ่าย แลกเปลี่ยน และเปิดวิธีการ |

### 4.2 อาชีพเริ่มต้นสิบสาย

ผู้เล่นอาจกำหนดอาชีพอิสระ แต่การเลือก starter template จะให้แกน ความชำนาญ ของเริ่มต้น แรงกดดัน และภารกิจแรกที่มีโครงพร้อมเล่น

| Template | จุดแข็งของเรื่อง | แรงกดดันเปิดเรื่อง |
|---|---|---|
| **โคคูจิน / เจ้าเมืองชายแดน** | ที่ดิน เครือญาติ การประชุม | บ้านใหญ่สองฝ่ายต้องการข้าวและแรงงาน |
| **จิซามูไร / ซามูไรชาวนา** | หมู่บ้าน ผลผลิต การระดมคน | เก็บเกี่ยวปะทะการเกณฑ์แรงงาน |
| **โรนิน / ผู้ไร้นาย** | อาวุธ เดินทาง เอาตัวรอด | ด่านถามว่าเป็นคนของใคร |
| **พ่อค้าเมืองซะไก** | บัญชี เครดิต เส้นทาง | สินค้าถูกตรวจและคู่แข่งรู้ชื่อ |
| **ช่างยุทโธปกรณ์ / ช่างปืนไฟ** | โลหะ ซ่อม ตรวจร่องรอย | งานช่างถูกโยงกับคนผิดฝ่าย |
| **ผู้สืบข่าวจากเครือข่าย** | เส้นทาง สัญญาณ ข่าว | ข้อมูลต้องผ่านด่านโดยไม่เปิดตัว |
| **ผู้คุ้มกัน寺社 / คนของวัด** | ไกล่เกลี่ย เอกสาร ผู้ลี้ภัย | ที่พักพิงถูกบีบให้เลือกข้าง |
| **คนสนิทไดเมียว** | พิธีสาร คำสั่ง อ่านอารมณ์ | คำสั่งเร็วและความระแวงในบ้านใหญ่ |
| **ผู้พิทักษ์ปราสาทแนวหลัง** | คลัง เสบียง คนในเรือน | ผู้ลี้ภัยปะทะเสบียงรับการล้อม |
| **หัวหน้ากองเรือ / ซุยกุน** | ทางน้ำ ลูกเรือ ค่าผ่าน | สิทธิ์ในช่องแคบและคำค้ำทางเรือ |

### 4.3 คำถามแรงดึงหกข้อ

คำตอบไม่ใช่ faction lock และไม่ใช่ stat bonus โดยตรง แต่เป็นบ่อเกิดของภารกิจ NPC ความทรงจำ และทางเลือกที่ควรกลับมาทวงผู้เล่นในเวลาที่เหมาะสม

| ID | คำถาม | Tag หลัก |
|---|---|---|
| `first_survivor` | เมื่อกลองสงครามดังขึ้น เจ้าอยากให้ใครรอดก่อนเป็นคนแรก | family, protection |
| `stance` | หากต้องยืนข้างใครสักฝ่าย เจ้าจะยืนข้างใคร หรือจะไม่ยืนข้างใครเลย | allegiance, politics |
| `never_surrender` | มีใครหรือสิ่งใดที่เจ้าจะไม่ยอมมอบให้ผู้มีอำนาจ | oath, resistance |
| `debts` | ใครติดหนี้เจ้า และเจ้าติดหนี้ใคร | debt, obligation |
| `hidden_knowledge` | เจ้ารู้สิ่งใดที่คนอื่นต้องการ แต่ยังไม่รู้ว่าเจ้ามี | secret, leverage |
| `sacrifice` | หากต้องเสียบางอย่างเพื่อให้บ้านรอด เจ้าจะยอมเสียอะไร | sacrifice, home |

นักพัฒนาควรให้คำตอบเหล่านี้กลับมาในรูป **เหตุการณ์**, **คำขอ**, **คนที่ได้รับผล**, หรือ **ราคาที่ถูกทวง** ไม่ใช่ป๊อปอัปที่บอกว่าผู้เล่นได้แต้มเรื่องราว

## 5. สถานะ ทรัพยากร และผลตามมา

### 5.1 Vitals

| ค่า | ความหมายเชิงเรื่อง | สถานะ rule loop ปัจจุบัน |
|---|---|---|
| **Wounds / บาดแผล** | อาการที่ทำให้ทุกการตัดสินใจมีต้นทุนทางกาย | เก็บและแสดงผลแล้ว; ยังไม่มี penalty/healing threshold ครบวงจร |
| **Focus / ค่าสติ** | ความสามารถรักษาการตัดสินใจท่ามกลางความหวาดกลัว ความอับอาย หรือแรงกดดัน | เก็บและแสดงผลแล้ว; ยังไม่มี stress/recovery loop ครบวงจร |
| **Momentum / แรงฮึด** | แรงฝืนชั่วคราวที่ใช้พลิก margin | ใช้ +2 หลังทอยได้จริง |

### 5.2 สถานะทางสังคม

| ค่า | ความหมาย | การเปลี่ยนอัตโนมัติปัจจุบัน |
|---|---|---|
| **Rank** | ตำแหน่งและสิทธิ์ที่ถูกมองเห็น | เก็บข้อมูล; ยังไม่เป็น access check เต็มระบบ |
| **Honor** | ความน่าเชื่อถือของคำมั่นหรือชื่อ | เก็บข้อมูล; ยังไม่คำนวณอัตโนมัติทุกฉาก |
| **Influence** | น้ำหนักต่อรองในเครือข่าย | เก็บข้อมูล; ยังไม่มี faction reaction เต็มระบบ |
| **Information** | ข่าว/หลักฐานที่ตัวละครถืออยู่ | Local Trial เพิ่ม +1 เมื่อ `partial_success` |
| **Stain** | รอยข้อครหา ความผิดพลาด หรือชื่อเสีย | Local Trial เพิ่ม +1 เมื่อ `failure_with_consequence` |

### 5.3 ทรัพยากรและชุมชน

`property`, `supplies`, และ `credit` เป็นทรัพยากรของตัวละคร ไม่ควรถูกตีความเป็นเงินเหรียญชนิดเดียว Property คือสิ่งที่ยอมจ่ายหรือแลกได้ Supplies คือสิ่งยังชีพและการเตรียมตัว ส่วน Credit คือสิทธิ์ที่เครือข่ายพร้อมเชื่อว่าตัวละครมี

ชุมชนมี `food`, `labor`, `voice`, `safety`, `cohesion` เพื่อรองรับผลที่กว้างกว่าตัวละครหนึ่งคน ปัจจุบันเก็บข้อมูลไว้แล้ว แต่ยังไม่เกิด consumption, seasonal pressure หรือ consequence อัตโนมัติครบวงจร

## 6. ฉาก ภารกิจ และความทรงจำของโลก

### 6.1 ฉาก (`Scene`)

ฉากคือหน่วยเล่าเรื่องที่ต้องมีสถานที่ สิ่งที่คนทั่วไปเห็น แรงกดดัน ผู้พูด คำถาม และทางเลือกที่ชวนลงมือ ไม่ใช่บทบรรยายปิดตาย

```ts
type Scene = {
  id: string;
  chapter: string;
  title: string;
  location: string;
  publicContext: string;
  body: string[];
  speaker: string;
  prompt: string;
  pressure: string;
  suggestedActions: string[];
}
```

ฉากเปิดและผล local resolution ต้องเน้นรายละเอียดทางกายภาพ บทสนทนาของ NPC และราคาที่จับต้องได้ ไม่ควรเขียนว่า “เรื่องเดินต่อ” โดยไม่บอกว่าใครได้เสียอะไร

### 6.2 ภารกิจ (`Mission`)

ภารกิจสร้างมาจากผู้มอบงาน ฐานะของผู้มอบ งานที่ขอ แรงกดดัน เส้นตาย รางวัล ความเสี่ยง และทางเลือก ไม่ควรให้รางวัลเป็นเงินสดเป็นค่าตั้งต้นเสมอไป

| ผู้มอบงาน | รางวัลที่ควรเหมาะกับฐานะ | ต้นทุนที่ควรนึกถึง |
|---|---|---|
| ชาวบ้าน | เสบียง แรงงาน ที่พัก ความคุ้มครองของชุมชน | ใครต้องทำงานแทน, ฤดูเก็บเกี่ยว, ความปลอดภัยของบ้าน |
| ซามูไร/บ้านใหญ่ | ใบผ่าน การคุ้มครอง สิทธิ์เข้าถึง ข่าว | ถูกผูกชื่อ, พยาน, คำสั่งที่ทำร้ายคนอื่น |
| พ่อค้า | เครดิต ข้อมูล เส้นทาง สินค้าหายาก | หนี้ คู่แข่ง หลักฐานบัญชี |
| วัด/ศาลเจ้า | ที่พักพิง ข่าว คนกลาง เอกสารรับรอง | ความเป็นกลาง การถูกกล่าวหา และผู้ลี้ภัย |
| ผู้ปกครอง | คำรับรอง สิทธิ์ผ่านทาง ทรัพยากรบ้านใหญ่ | ความใกล้อำนาจและความเสี่ยงถูกโยงกับการกวาดล้าง |

**สถานะปัจจุบันของ core:** ภารกิจเริ่มที่ `offered`, เปลี่ยนเป็น `active` เมื่อรับ, และ `applyRoll()` จะอัปเดตภารกิจรายการแรกเป็น `resolved` เมื่อผลไม่ใช่ failure หรือ `active` เมื่อพลาด นี่เป็น vertical-slice rule ไม่ใช่ mission engine สมบูรณ์ นักพัฒนาต้องไม่แอบอ้างว่า objective chain, expiry, reward distribution หรือหลายภารกิจ active ทำงานครบแล้ว

### 6.3 ความทรงจำโลก (`WorldMemory`)

Memory คือหลักฐานว่าโลกจำอะไร ไม่ใช่แค่ข้อความเก็บ log

| Kind | ใช้กับ | ตัวอย่าง |
|---|---|---|
| `news` | ข่าวหรือเหตุการณ์เปิดเรื่อง | ข่าวด่านปิด, ข่าวเรือหาย |
| `witness` | คนเห็นการกระทำหรือผลที่สำเร็จมีราคา | ผู้คุมเห็นการใช้เอกสาร |
| `debt` / `favor` | การติดค้างหรือรับน้ำใจ | กันทาโร่ช่วยจากน้ำ |
| `oath` | คำสาบานหรือคำรับรอง | ยืนข้างหมู่บ้านต่อหน้าคนกลาง |
| `stain` | รอยข้อครหาและความพลาด | แผนพังจนชื่อถูกจด |
| `injury` | บาดแผลหรือผลทางกาย | แขนใช้ได้จำกัด |
| `market_change` | ผลของการซื้อหรือการแลกเปลี่ยน | รับยาแบบค้ำประกัน |
| `community_change` | การเปลี่ยนของชุมชน | อาหารลด, ความปลอดภัยดีขึ้น |
| `actor_relation` | ความสัมพันธ์กับ NPC | คนส่งสารเริ่มไม่ไว้ใจ |

## 7. ตลาด สัมภาระ หนี้ และบุญคุณ

### 7.1 หลักเศรษฐกิจของ Dust & Fire

ตลาดไม่ใช่ร้านที่มีทุกอย่างตลอดเวลา ราคาและความพร้อมต้องมีเหตุผลจากฤดู เส้นทาง การตรวจ การสงคราม ความขาดแคลน และเครือข่ายผู้ขาย ทุกการแลกเปลี่ยนควรมีอย่างน้อยหนึ่งอย่าง: **ราคา, เวลา, เงื่อนไข, พยาน, หรือผลตามมา**

### 7.2 สัมภาระ (`InventoryItem`)

| ประเภท | ความหมาย | ตัวอย่างการใช้งานในกติกา |
|---|---|---|
| `immediate` | ใช้ได้ทันทีในฉาก | เครื่องมือหรือสิ่งที่ตอบสถานการณ์เฉพาะหน้า |
| `reserve` | เสบียง/ของที่ใช้ภายหลัง | ข้าวตาก ยา ผ้า เชือก |
| `equipment` | อุปกรณ์ที่ให้ความได้เปรียบ | ปืน เครื่องมือช่าง |
| `document` | เอกสารที่เปิดทางหรือสร้างความเสี่ยง | ตรา หนังสือผ่านทาง บัญชี |
| `status` | สิ่งที่บ่งผลต่อสภาพตัวละคร | ผ้าพันแผลชุ่มยา |
| `bond` | วัตถุที่ผูกกับความสัมพันธ์/เครือข่าย | เชือกสัญญาณ กุญแจคลัง |

ของชิ้นหนึ่งมี `condition`, `location`, `ownership`, `slots`, และ optional bonus ที่ผูกกับ axis/แท็ก ปัจจุบัน Local Trial ตรวจโบนัสเฉพาะไอเทม `usable` ที่แท็กสอดคล้องกับ action หรือ mastery tags

> ข้อจำกัดปัจจุบัน: การกินยา ซ่อมของ สวมอุปกรณ์ ย้ายเก็บ โอนให้คนอื่น บังคับ slot capacity และทำของเสียหายจาก action ยังไม่เป็น action loop สมบูรณ์

### 7.3 ข้อเสนอในตลาด (`MarketOffer`)

Market Offer เป็น goods, service หรือ information และควรมี `priceReason` เพื่อไม่ให้ราคาดูสุ่มโดยไร้บริบท เมื่อซื้อ goods ที่รองรับ ระบบลด `property`, เพิ่ม item เข้า inventory, ทำให้ offer นั้น `available: false`, เขียน transaction และสร้าง market memory

### 7.4 บริการ (`MarketService`)

บริการต้องเก็บข้อมูลมากกว่าราคา

```text
Provider + Role + Affiliation
Request + Price + Time Cost + Requirement
Witness Risk + Availability
```

แม้การว่าจ้างบริการยังไม่ resolve เวลาและผลลัพธ์ครบวงจร โครงนี้คือ contract ที่ต้องรักษาเมื่อนำ action loop มาเพิ่ม: ผู้เล่นควรเห็นว่ากำลังขอใคร ทำให้ใครรู้ ใช้เวลาเท่าใด และจะติดอะไร

### 7.5 หนี้ เครดิต และบุญคุณ (`Obligation`)

| Kind | ความหมาย | คำถามที่ต้องตอบเมื่อใช้ในฉาก |
|---|---|---|
| `credit` | สิทธิ์ที่เครือข่ายยอมให้ใช้ก่อน | ใครรับรอง? เงื่อนไขใดจะทำให้เครดิตหมด? |
| `debt` | สิ่งที่ตัวละครติดค้าง | ต้องชำระอะไร เมื่อใด และใครเป็นพยาน? |
| `favor` | บุญคุณหรือหน้าที่ตอบแทนที่ไม่ควรถูกตีเป็นเหรียญ | ใช้ได้เรื่องใด? การเรียกใช้ทำลายความสัมพันธ์หรือไม่? |

Obligation ทุกชิ้นควรมี `holder`, `subject`, `due`, `witness`, `status`, และ `note` เพื่อให้หนี้เป็นเรื่องเล่าเชิงสังคม ไม่ใช่ตัวเลขลอย ๆ

### 7.6 กรณีศึกษา: ยาสมุนไพรเซฟเฮาส์ไซกะ

ในเซฟตัวอย่างไซกะ ผู้เล่นที่ทรัพย์สินไม่พออาจรับยาสมุนไพรได้ หากหนี้ของเซฟเฮาส์ยังเปิดอยู่และกันทาโร่ค้ำให้ ระบบจะไม่หัก property, อัปเดต note และ due ของหนี้, เขียน `ExchangeRecord` ประเภท debt, และเพิ่ม `WorldMemory` ว่าผู้เล่นรับของแบบค้ำประกันแล้ว

นี่คือรูปแบบที่ควรนำไปใช้ต่อกับบริการและบุญคุณ: **การได้สิ่งของทันทีต้องแลกด้วยสิ่งที่โลกเก็บไว้ทวงภายหลัง**

## 8. ขอบเขตประวัติศาสตร์และการเขียนนิยาย

### 8.1 สถานะประวัติศาสตร์สี่แบบ

| Status | ใช้เมื่อ | สิ่งที่ GM/ผู้เขียนต้องทำ |
|---|---|---|
| `fact-supported` | ข้อความเฉพาะได้รับการรองรับโดย fact card ที่ส่งเข้า context | บอกได้เฉพาะขอบเขตที่หลักฐานสนับสนุน |
| `contextual-play` | ข้อเท็จจริงเชิงโครงสร้างถูกใช้สร้างฉากสมมติ | แยกให้ชัดว่าโครงสร้างมีหลักฐาน แต่ NPC/เหตุการณ์เป็นของแคมเปญ |
| `campaign-fiction` | รายละเอียดเป็นเรื่องสมมติของเกม | ไม่เขียนให้เหมือนเป็นเหตุการณ์จริง |
| `insufficient-evidence` | คำขอเกินข้อมูลที่คัดสรรไว้ | บอกว่าหลักฐานไม่พอ แทนการเดา |

### 8.2 กฎสำหรับเนื้อหา

1. อย่าประกาศว่า NPC สมมติมีตัวตนจริง
2. อย่าใช้ข้อเท็จจริงเชิงโครงสร้างเป็นกฎตายตัวว่าทุกแคว้น ทุกวัด หรือทุกชนชั้นต้องทำเหมือนกัน
3. อย่าสร้างตำแหน่งราชการ กฎหมาย หรือธรรมเนียมเฉพาะถิ่นที่แม่นยำเกิน fact card แล้วนำเสนอเป็นความจริง
4. ใช้ปี ฤดู แคว้น และ domain ของฉากเพื่อตัด fact cards ที่อยู่นอกยุคหรือไม่เกี่ยวข้องออก
5. เมื่อข้อมูลไม่พอ ให้เขียนแรงกดดันที่เป็น fiction อย่างซื่อตรง แทนการเติม “เกร็ดประวัติศาสตร์” ปลอม

### 8.3 Domain ที่ historical selector ใช้

ระบบจับคำใน action และ scene เพื่อเลือก fact cards ตาม domain: `market`, `travel`, `faith`, `war`, `season`, `health`, `language`, `maritime`; หากไม่พบจะใช้ `status` และ `household` เป็น fallback เฉพาะการคัดข้อมูล ไม่ได้แปลว่าฉากได้รับการยืนยันว่าเกิดขึ้นจริง

## 9. AI GM และ Local Trial

### 9.1 หน้าที่ที่แยกจากกัน

| ชั้นระบบ | หน้าที่ | ห้ามทำ |
|---|---|---|
| **Deterministic engine** | เลือก/ยืนยันแกน, ทอย 2d12, รวมค่า, คำนวณ outcome, ใช้ Momentum, อัปเดต state | ให้โมเดลเปลี่ยน total, reward, resource หรือ outcome |
| **AI GM** | ตีความ intent, เสนอ mastery/context, เขียนฉากผล, ชี้ historical boundary | ทอยแทนผู้เล่น, บวกโบนัสเกิน +2, สร้างประวัติศาสตร์เทียม |
| **Local Trial** | ทำ action analysis และ narration ด้วยกฎเชิง deterministic ในเครื่อง | เรียก AI หรือหักเครดิต AI |

### 9.2 สัญญา AI GM ก่อนทอย

Input ของ AI GM รับ action, language และ game context ที่ย่อแล้ว ผลต้องมี `intentSummary`, axis, suggested mastery, difficulty, context bonus/reason, risk, confirmation และ historical boundary

ผล difficulty ของ AI อยู่ในช่วง 5–30 แต่ต้อง normalize เข้าสู่ tier ของ client. Bonus ต้อง clamp อยู่ 0–2. Mastery ที่ AI ส่งกลับต้องเป็นชื่อเดียวกับ mastery ใน context หรือ `null` เท่านั้น

### 9.3 สัญญา AI GM หลังทอย

AI GM ได้รับ roll ที่ deterministic engine ตัดสินแล้ว และต้องตอบ

| ฟิลด์ | กติกา |
|---|---|
| `sceneTitle` | ชื่อฉากต่อเนื่อง |
| `narration` | **3 ย่อหน้าพอดี** ย่อหน้าละ 120–1,100 ตัวอักษร |
| `nextChoices` | **3 ทางเลือก** ที่สั้นและเกิดจากฉากจริง |
| `memory` | ผลเปลี่ยนสำคัญ ไม่ใช่สรุปเรื่องทั้งตอน |
| `missionNote` | ข้อสังเกตต่อภารกิจ |
| `historicalFence` / `historicalStatus` | ขอบเขตเชิงประวัติศาสตร์ |

ฉาก AI ต้องมีรายละเอียดประสาทสัมผัสหรือกายภาพ, ปฏิกิริยา/คำพูดของ NPC, และผลที่จับต้องได้ ห้ามพูดถึงเต๋า DN กฎ เครดิต โมเดล หรือ prompt ในเนื้อเรื่อง

### 9.4 เวลาและ fallback

การเรียก AI GM ถูก abort ที่ **45 วินาที** เมื่อ provider ไม่ตอบ และการตรวจระบบล่าสุดพบ provider ตอบ `412 usage exhausted` จึงทำให้ Local Trial เป็นคอร์ที่ใช้งานได้จริงในปัจจุบัน หาก AI path เปิดอยู่แล้วล้ม ระบบต้อง

1. resolve แบบ deterministic ในเครื่อง
2. เขียน roll, scene, memory และ Local Save ตามปกติ
3. ไม่หัก AI credit
4. แจ้งผู้เล่นอย่างชัดว่าได้ใช้ Local Trial

> **กฎสำคัญสำหรับนักพัฒนา:** อย่าให้ความต่อเนื่องของแคมเปญขึ้นอยู่กับ AI provider. AI GM เป็นความสามารถเสริมด้านการตีความและร้อยแก้ว ไม่ใช่ authority ของกติกา

## 10. คู่มือนักพัฒนา: โมเดลข้อมูลและ invariant

### 10.1 GameState คือ single source of truth ฝั่งแคมเปญ

```ts
type GameState = {
  schemaVersion: 2;
  credits: number;
  campaign: CampaignContext;
  character: Character;
  community: Community;
  currentScene: Scene;
  missions: Mission[];
  market: MarketOffer[];
  economy: EconomyState;
  memories: WorldMemory[];
  rolls: RollRecord[];
  historicalBoundary?: HistoricalBoundary & { tick: number };
  tick: number;
}
```

### 10.2 Invariant ที่ต้องรักษา

| Invariant | เหตุผล |
|---|---|
| `tick` ต้องเพิ่มเมื่อเกิด roll ที่ resolve แล้ว | ทำให้ log, memory, exchange และ Leaf เรียงตามเหตุการณ์ได้ |
| `record.tick === state.tick + 1` ก่อน `applyRoll` | รักษาลำดับผลทอยและฉากถัดไป |
| `momentumSpent` เป็น 0 หรือ 2 แต่ลด vital momentum จริงเพียง 1 | แยกค่าที่บวกในสูตรออกจากจำนวน token ที่ใช้ |
| `MarketOffer.available` ต้องเป็น `false` หลังรับข้อเสนอสำเร็จ | ป้องกันซื้อซ้ำใน state เดียวกัน |
| ทุก transaction ที่สำคัญต้องมี `counterpart`, `payment`, `witness`, `consequence`, `tick` | ให้เศรษฐกิจมีร่องรอยที่ย้อนอ่านได้ |
| สถานะ history ต้องอยู่ในสี่ค่าเท่านั้น | ป้องกัน UI/AI แสดงความมั่นใจเทียม |
| `economy` ต้องมีเสมอใน schema v2 | Local Save เก่าต้องผ่าน `normalizeGameState()` ก่อนใช้งาน |

### 10.3 Migration ของเซฟ

เซฟรุ่นเก่าที่ไม่มี `economy` ไม่ควรทำให้เกม crash. `normalizeGameState()` ต้องเติม `buildSaikaEconomy()` ให้แคมเปญไซกะ หรือ `buildCampaignEconomy(campaign)` ให้แคมเปญอื่นก่อน state ถูกส่งเข้ากฎหรือ content ที่ต้องใช้ economy

เมื่อต่อ schema ในอนาคต ให้เพิ่ม versioned migration แบบ pure function แทนการกระจาย optional chaining ทั่วโค้ด ตัวอย่างแนวคิด:

```ts
function migrateGameState(raw: unknown): GameState {
  // detect version → enrich defaults → validate → return canonical vNext state
}
```

### 10.4 ขอบเขต persistence

| ชั้น | เก็บอะไร | สถานะปัจจุบัน |
|---|---|---|
| **Local browser** | GameState, campaign library, save slots, settings | แหล่งจริงของแคมเปญและเรื่องราว |
| **Backend database** | OAuth user และ `trialCredits` | ไม่มีตาราง campaign/scene/log/inventory |
| **AI provider** | วิเคราะห์และบรรยายแบบชั่วคราว | ไม่ใช่ที่เก็บ state และอาจใช้งานไม่ได้ |

ก่อนเพิ่ม cloud save ต้องออกแบบ identity ของ save, revision, conflict policy, export/import และสิทธิ์เข้าถึงให้ครบ ไม่ควรย้าย Local Save ขึ้นฐานข้อมูลโดยไม่มี migration และ versioning

## 11. คู่มือนักพัฒนา: ลำดับการ resolve

### 11.1 Local Trial flow

```text
Declared action
  → parseAction(action, state)
  → RollPreview
  → resolveRoll(preview, state, spendMomentum)
  → RollRecord
  → applyRoll(state, record)
  → GameState ใหม่
  → persist Local Save
```

### 11.2 `parseAction()` ในเวอร์ชันปัจจุบัน

1. normalize action เป็นตัวพิมพ์เล็ก
2. หา keyword ชุดแรกที่ตรง แล้วใช้ axis/method/mastery tags ของชุดนั้น; หากไม่ตรงใช้ `wit` เป็น fallback
3. sort mastery จาก tag match ก่อน แล้วค่อยระดับสูง
4. หา inventory item ที่ `usable` และ bonus tags ตรงกับ action หรือ mastery tags
5. ประเมิน risk:
   - มีคำว่า ฆ่า/ปลอม/ขโมย/บุก → direct risk, DN 22
   - มีคำว่า ด่าน/ผู้คุม/ค่าย → difficult, DN 18
   - action สั้นกว่า 12 ตัวอักษร → DN 10
   - นอกนั้น → DN 14
6. สร้าง risk และ witness list จากระดับความเสี่ยง

นี่คือ heuristic ที่ตั้งใจให้เรียบง่ายและ deterministic ไม่ใช่ semantic parser ที่เข้าใจทุกเจตนา เมื่อขยายระบบ ควรแยก intent parsing ออกจาก difficulty reasoning และให้ tests ครอบคลุมภาษาไทยหลายรูปแบบก่อนเปลี่ยน keyword map

### 11.3 `resolveRoll()` และ `applyRoll()`

`resolveRoll()` เป็น pure-ish calculation ที่สร้าง RollRecord โดยสุ่ม d12 สองลูกและไม่แก้ state เดิม. `applyRoll()` เป็นขั้นที่แก้ state แบบ immutable: ลด Momentum เมื่อใช้, เพิ่ม Stain เมื่อ failure, เพิ่ม Information เมื่อ partial, เขียน memory, ต่อ scene, เปลี่ยนสถานะภารกิจแรก และเพิ่ม tick

ห้ามให้ AI GM เข้าไปแก้ `total`, `margin`, `outcome`, `momentumSpent`, หรือ resource โดยตรง หากต้องการผลจาก AI ให้แปลงเป็น event ที่ deterministic application layer ตรวจ/ยอมรับอีกชั้นหนึ่ง

### 11.4 รูปแบบ event ที่ควรเพิ่มในอนาคต

เมื่อเกมซับซ้อนขึ้น ควรย้ายผล side effect ออกจาก `applyRoll()` แบบรวมศูนย์ไปยัง event ที่ตรวจสอบได้ เช่น

```ts
type GameEvent =
  | { type: "roll_resolved"; record: RollRecord }
  | { type: "mission_progressed"; missionId: string; stepId: string }
  | { type: "obligation_called"; obligationId: string }
  | { type: "inventory_consumed"; itemId: string; quantity: number }
  | { type: "community_changed"; field: keyof Community; delta: number; reason: string };
```

แนวนี้ช่วยทำ replay, debug, timeline, cloud sync และ narrative audit ได้ง่ายขึ้น แต่ไม่จำเป็นต้องทำก่อน mission/economy action loop ที่ผู้เล่นต้องใช้จริง

## 12. การเขียนเนื้อหาและการทดสอบ

### 12.1 มาตรฐานฉาก

ฉากเปิดควรมีอย่างน้อยสามจังหวะ: สภาพแวดล้อมที่จับต้องได้, NPC ที่แสดงแรงกดดันผ่านท่าทีหรือคำพูด, และทางเลือกที่มีราคา ฉากหลังทอยต้องไม่ตัดไปสรุปเร็วจนผู้เล่นมองไม่เห็นผลที่ตนก่อ

| ควรทำ | ไม่ควรทำ |
|---|---|
| ให้กลิ่น เสียง ผิวสัมผัส หรือการเคลื่อนไหวหนึ่งถึงสองอย่างจากบริบทจริงของฉาก | วางคำบรรยายสากลซ้ำ ๆ โดยไม่ผูกกับสถานที่และฤดู |
| ให้ NPC ตัดสินใจหรือแสดงท่าทีต่อผล | เขียนว่า “NPC ยอมรับ” โดยไม่บอกว่าเขาสูญเสียอะไร |
| ลงผลให้เป็นหนี้ พยาน ข่าว เวลา ของ หรือเส้นทาง | เขียน “เกิดผลตามมา” แบบไม่มี object |
| ปล่อยให้ failure เปิดงานแก้ใหม่ | จบเรื่องด้วย “ทำไม่ได้” แล้วไม่มีทางเล่นต่อ |

### 12.2 ขอบเขตการทดสอบขั้นต่ำ

| ระบบ | Regression ที่ควรมี |
|---|---|
| 2d12 | Margin แต่ละช่วงให้ outcome ถูกต้อง; Momentum ใช้/ไม่ใช้ถูกต้อง |
| Action parser | คำไทยสำคัญพาไป axis และ difficulty ที่คาดได้ |
| Scene/log | ฉากเปิดและ post-roll มีเนื้อเรื่องหลายย่อหน้า ผลที่บันทึกตรง Leaf |
| Historical fence | ครบทั้ง four statuses และไม่มี label หลุดเข้า narrative |
| Market | ซื้อสำเร็จลด property/ปิด offer/เพิ่ม transaction; ยาค้ำประกันเพิ่มร่องรอยหนี้ |
| Local Save | restore slot, campaign switching และ migration เซฟเก่าที่ไม่มี economy |
| AI failure | error/timeout ทำ fallback Local Trial, ไม่หักเครดิต, และเซฟ roll/Leaf จริง |
| Backend credits | ใช้ transaction ที่หักเฉพาะผู้ใช้ที่ authenticated และไม่ติดลบ |

### 12.3 หลักความปลอดภัยและความถูกต้อง

1. ตรวจ input ของ AI ด้วย schema ทั้งก่อนส่งและหลังรับ
2. clamp numeric value ที่ AI ส่งเสมอ
3. ไม่ส่ง secret หรือข้อมูลของผู้เล่นคนอื่นใน GM context
4. ไม่เรียก provider ใน Local Trial
5. อย่าใช้ AI output เป็นคำสั่ง SQL หรือ code execution
6. บันทึกว่าเนื้อหาใดเป็น historical fence ไม่ใช่ปล่อยให้ผู้เล่นคิดว่า fiction คือ fact

## 13. สถานะปัจจุบันและ roadmap คอร์เกม

### 13.1 สิ่งที่เป็น playable core แล้ว

| คอร์ | สถานะ |
|---|---|
| การสร้างตัวละครจาก 10 template หรืออาชีพอิสระ | ใช้งานได้ |
| ความสัมพันธ์หกข้อและข้อมูลตัวตน | ใช้งานได้ |
| ประกาศ action หนึ่งประโยค → วิเคราะห์ → 2d12 → ผล → ฉากต่อ | ใช้งานได้ใน Local Trial |
| Momentum, memory, log และ Local Save | ใช้งานได้ |
| ภารกิจแรกและผลสถานะพื้นฐาน | ใช้งานได้แบบ vertical slice |
| ตลาดห้าบัญชีและ selected market purchase | ใช้งานได้บางส่วน |
| หนี้ค้ำประกันในเซฟไซกะ | ใช้งานได้ |
| historical boundary และ structured AI GM contract | สร้างแล้ว; provider เป็น optional availability |

### 13.2 สิ่งที่เก็บข้อมูลแล้ว แต่ต้องสร้าง action loop

| ระบบ | ลำดับที่ควรสร้าง |
|---|---|
| **Mission engine** | objective steps, progress, expiry, rewards, issuer reactions, multiple active missions |
| **Inventory engine** | use, consume, repair, equip, transfer, capacity, condition change |
| **Service / obligation engine** | hire service, advance time, call favor, settle debt, create counteroffer, witness repercussion |
| **Vitals / community engine** | healing, stress, supplies, seasonal pressure, community deltas, social access checks |
| **World engine** | NPC state, discovered facts, timeline, place map, event replay |

### 13.3 ลำดับพัฒนาที่แนะนำ

1. **ทำ Mission Progress และ Consequences ให้เต็มวงจร** เพราะภารกิจคือเครื่องยนต์กำหนดเหตุผลของการกระทำ
2. **ทำ Inventory, Services, Debt และ Favor Actions** เพื่อให้ตลาดไม่เป็นเพียงบัญชีอ่าน
3. **ทำ Vitals, Supplies, Community และ Social Access** เพื่อให้การตัดสินใจสะสมผลข้ามฉาก
4. **ทำ NPC/World Timeline/Map State** เพื่อให้โลกมีความต่อเนื่องในระดับสถานที่และเวลา
5. **ทำ export/import และ cloud persistence** หลัง schema และ event model เสถียร
6. **เปิด AI GM เป็น optional enhancement** เมื่อ provider capacity พร้อม โดยไม่ลดความสามารถของ Local Trial

> เกณฑ์ความสำเร็จของเกมเต็มไม่ใช่ “มีหน้าข้อมูลครบ” แต่คือผู้เล่นสามารถทำสิ่งสำคัญในเรื่อง—รักษาแผล ใช้ของ ต่อรองหนี้ เรียกคนช่วย ทำงานให้เสร็จ หรือทำลายความไว้วางใจ—แล้วโลกตอบกลับด้วย state, memory และฉากที่สอดคล้องกันโดยไม่ต้องให้ AI มาอุดช่องว่างของกติกา
