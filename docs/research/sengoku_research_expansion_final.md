# Sengoku Historian + World State Research Expansion

## คำตอบสำหรับทีมเกม

ข้อเสนอหลักคือ **ไม่ควรสร้างเมนูใหญ่แยกสามระบบเป็น Reputation, Heat และ Seasonal Pressure คนละเมนู** เพราะผู้เล่นจะรู้สึกว่าเป็นระบบบัญชีสามชุดที่ต้องเปิดตรวจตลอดเวลา ควรเพิ่มข้อมูลสั้นลงในช่องเดิมของหน้าสนทนา แผนที่ แคว้น และตัวละคร แล้วสร้างเมนูใหญ่เพียงเมนูเดียวชื่อ **“เครือข่ายอำนาจและข่าวสาร”** (Power & Rumor Network) สำหรับการวางแผนระยะกลาง–ยาว เมนูนี้รวม faction, ข่าวลือ, ความเสี่ยง, เส้นทางสินค้า และแรงกดดันฤดูกาลไว้ในแผนที่เดียว

ในทางประวัติศาสตร์ ชื่อเสียงไม่ควรเป็น “ค่าความดี” ของตัวละคร แต่ควรเป็นความทรงจำและการประเมินของกลุ่มที่มีผลประโยชน์ต่างกัน ชาวบ้านอาจเห็นผู้เล่นเป็นผู้คุ้มครอง ขณะที่ซามูไรของเจ้าแคว้นมองว่าเป็นตัวแปรอันตราย และสภาพ่อค้าอาจไว้ใจผู้เล่นเฉพาะเมื่อชำระหนี้ตรงเวลา ระบบ Heat ก็ควรเป็นความเสี่ยงที่มีขอบเขตพื้นที่และฝ่าย ไม่ใช่ดวงตาของโลกที่รู้ทุกอย่าง ส่วนฤดูกาลควรกดดันแรงงาน เสบียง ถนน แม่น้ำ ทะเล และราคา แต่ต้องเปิด “หน้าต่างโอกาส” ให้ผู้เล่นวางแผนได้ ไม่ใช่ลงโทษแบบสุ่ม

รายงานนี้แยก **หลักฐานประวัติศาสตร์**, **ข้อสังเคราะห์จากหลายหลักฐาน**, **ข้อถกเถียง/ข้อจำกัด**, และ **การแต่งเติมเพื่อเกม** ไว้คนละส่วน เมื่อใช้ศัพท์ญี่ปุ่น จะระบุว่าศัพท์นั้นมีความหมายกว้างหรือเปลี่ยนตามพื้นที่ ไม่ใช้ระบบชนชั้นแบบ Edo ย้อนกลับไปครอบคลุม Sengoku โดยอัตโนมัติ

## 2. สิ่งที่ภาษาญี่ปุ่นช่วยแก้ความเข้าใจผิด

### 2.1 อย่าใช้ “ชาวนา–ซามูไร–พ่อค้า” เป็นกล่องตายตัว

บทความของ Kyoto Tachibana University อธิบายคำว่า 「土豪」 (dogō) และ 「地侍」 (jizamurai) ว่าเป็นนักรบหน้าใหม่ที่มีรากจากเกษตรกรผู้มีอำนาจในหมู่บ้านหรือ荘園 ตั้งแต่ราวครึ่งหลังคริสต์ศตวรรษที่ 15 พวกเขาบริหารหมู่บ้าน เป็นผู้ใต้บังคับบัญชาของไดเมียวหรือ家臣 ออกรบ และทำหน้าที่เป็นตัวกลางการปกครองได้ ในกรณีศึกษาที่บทความยก เอกสารราว ค.ศ. 1550 แสดงนักรบเจ็ดคนจากชนบทใกล้ Kyoto ใต้ Miyoshi Nagayoshi ที่ร่วมออกคำสั่งงานก่อสร้าง Katsuryūji-jō [2]

สิ่งนี้ทำให้ NPC หนึ่งคนอาจเป็นผู้ถือที่นา ผู้ไกล่เกลี่ยน้ำ ผู้ส่งส่วย ผู้คุมกำลังหมู่บ้าน และนักรบในคนเดียวกันได้ การเปลี่ยนสังกัดหรือการกลับไปทำเกษตรไม่ใช่ความผิดปกติ งานวิจัยเดียวกันยังยกเส้นทางของตระกูลที่บางสายรับราชการทหารต่อ ขณะที่บางสายกลับเป็น庄屋/ผู้ใหญ่บ้านในยุคต่อมา [2] ดังนั้นฐานข้อมูลควรเก็บ **ตำแหน่ง เครือข่าย และทรัพยากร** แยกจาก `social_class` ค่าเดียว

### 2.2 “นินจา” ไม่ใช่คำตอบอัตโนมัติของทุกงานข่าวกรอง

แหล่ง National Diet Library ภาษาญี่ปุ่นระบุว่าเอกสารยุคสงครามใช้คำหลายแบบ เช่น 「くさ」 (kusa), 「かまり」 (kamari), 「透波」 (suppa) และ 「乱波」 (rappa) ส่วนคำเรียก 「忍者」 (ninja) เป็นคำที่นิยมในยุคใหม่กว่ามาก แหล่งเดียวกันอธิบายภารกิจที่เกี่ยวข้องกับการหลบซ่อน ลอบเข้า ทำลาย/ก่อกวน สอดแนม และการปฏิบัติงานที่เสี่ยงถึงชีวิต [3]

Japan Heritage ของ文化庁อธิบาย Iga และ Kōka ว่ามี地侍รวมตัวเป็น 「伊賀惣国一揆」 และ 「甲賀郡中惣」 ใช้การปรึกษาหารือและการรวมกลุ่มเพื่อปกป้องพื้นที่ บริบทภูมิประเทศเป็นหุบเขาและเนินเขาที่มี城館土塁หนาแน่น [4] แหล่งนี้เหมาะกับการออกแบบ faction แบบชุมชนทหารและเครือข่ายข่าว แต่ไม่ควรสรุปว่าทุกคนใน Iga/Kōka เป็นสายลับอาชีพหรือว่าภาพชุดดำ/อาวุธลับในสื่อเป็นหลักฐาน

## 3. Taxonomy คนทำงานล่าง–กลางสำหรับ NPC

| บทบาท/ศัพท์ | สถานะและงานที่มีหลักฐานสนับสนุน | ข้อจำกัด/สิ่งที่ไม่ควรเดา | แปลงเป็นเกม |
|---|---|---|---|
| **Rōnin / 浪人・牢人** | นักรบที่ไม่มีนายในช่วงเวลาหนึ่ง ไม่ใช่ “อาชีพ” แบบเดียว บางคนหานายใหม่ กลับหมู่บ้าน รับจ้างคุ้มกัน เข้ากลุ่มท้องถิ่น หรือกลายเป็นผู้พลัดถิ่น | ไม่ใช่ทุกคนเป็นนักดาบพเนจร และไม่ควรผูกกับภาพแบบ Edo หรือ 47 rōnin โดยอัตโนมัติ | ให้มีสถานะ `between_patronage`; จุดเด่นคือทักษะ/ข่าว/เครือข่าย แต่มีปัญหาเรื่องหลักประกันและความไว้ใจ |
| **Ashigaru / 足軽** | ทหารราบระดับล่างหรือกำลังที่ระดมมาใช้งาน บางคนมาจากหมู่บ้าน/เมือง บางคนมีประสบการณ์หรือสังกัดยาวนานขึ้นในคริสต์ศตวรรษที่ 16 | ไม่ใช่ “ชาวนาทั้งหมด” และไม่ใช่ซามูไรระดับเดียวกันทุกแคว้น; สถานะเปลี่ยนตามนายและยุค | แยก `levy_infantry`, `retained_infantry`, `ashigaru_taishō`; ให้ความก้าวหน้าผ่านความอยู่รอดและการอุปถัมภ์ ไม่ใช่เลเวลต่อสู้ล้วน |
| **Jizamurai / 地侍; Dogō / 土豪** | ผู้มีฐานที่ดินและอำนาจในท้องถิ่น มีส่วนบริหารหมู่บ้าน/น้ำ/แรงงาน เป็นตัวแทนของผู้ปกครอง และออกสงคราม [2] | ไม่ใช่ชนชั้นเดียวกับ daimyō; ฐานะและความเป็นอิสระต่างกันมาก | เป็น NPC สะพานระหว่างชาวนา วัด เจ้าแคว้น และสนามรบ มีทรัพยากรท้องถิ่นและความทรงจำยาว |
| **Kokujin / 国人** | นักรบ/ผู้มีอำนาจระดับภูมิภาคที่มีฐานในที่ดินและเครือญาติ อาจร่วมมือหรือขัดแย้งกับ daimyō | ขอบเขตและความหมายต่างกันตามแคว้น ไม่ควรใช้แทนทุกนักรบท้องถิ่น | เก็บเป็น faction node ที่มี loyalty แบบมีเงื่อนไขต่อผู้ปกครอง |
| **Shinobi / 忍び; kusa; kamari; suppa; rappa** | ผู้ทำงานสอดแนม ลอบเข้าเมือง หา/ส่งข่าว ก่อกวน หรือจู่โจมตามภารกิจและบริบทท้องถิ่น [3] | “Ninja” เป็นคำสมัยใหม่กว่า; ไม่มีหลักฐานว่าทุกคนแต่งชุดเดียวหรือทำงานเป็น assassin | ใช้ identity หลายระดับ เช่น scout, infiltrator, informant, guide; ให้ข่าวมี confidence และพยาน ไม่ใช่ข้อมูลจริงเสมอ |
| **ผู้ใหญ่/ตัวแทนหมู่บ้าน** | ใช้คำท้องถิ่นต่างกัน เช่น 乙名/otona, 年寄/toshiyori และในยุคต่อมามี 名主/myōshu หรือ 庄屋/shōya; งานคือรวบรวมคำสั่ง ภาษี น้ำ แรงงาน และการรักษาความสงบ | `nanushi/shōya` เป็นศัพท์ที่เด่นในระบบ Edo; อย่าย้อนเป็นตำแหน่งเดียวกันทุกหมู่บ้าน Sengoku | สร้าง hierarchy หมู่บ้านที่มี collective memory และการตัดสินใจแบบประชุม ไม่ใช่ NPC หัวหน้าคนเดียว |
| **Bugyō / 奉行; daikan / 代官; yūhitsu / 右筆** | เจ้าหน้าที่/คนเขียนคำสั่ง/ผู้ดูแลการบริหารของผู้มีอำนาจ งานจริงขึ้นกับบ้านและแคว้น | ชื่อตำแหน่งเดียวกันอาจมีอำนาจต่างกัน และเอกสารคนชั้นล่างมักมองผ่านงานภาษี/คดี | ให้เป็น NPC ที่ถือเอกสาร ตรา คลัง และลำดับคำสั่ง มีอำนาจเชิงข้อมูลมากกว่าพลังรบ |
| **เสมียนคลัง/ผู้ตรวจบัญชี** | ตรวจสิ่งของ ภาษี คลัง และการเบิกจ่าย; หลักฐานมักปรากฏในบัญชี/สัญญามากกว่าชีวิตส่วนตัว | อย่าสร้างตัวเลขเงินเดือนแม่นยำโดยไม่มีบัญชีเฉพาะ | เป็น gatekeeper ของเสบียงและใบผ่านทาง ความทรงจำของเขาผูกกับตรา/เอกสาร |
| **Sendō / 船頭; kajitori / 梶取; คนเรือ** | ผู้ควบคุมเรือ ผู้นำทาง ลูกเรือ และแรงงานขนถ่ายตามท่า; บทบาทสำคัญในทะเล Inland Sea, Biwa, Hakata และ Sakai | ชื่อเรียกและลำดับชั้นต่างกันตามชนิดเรือ/ท่า; ไม่เหมารวมคนเรือเป็นโจรสลัด | ทำระบบ reputation ต่อท่า/กัปตัน/นายท่า และ skill ด้านลม น้ำขึ้นลง เส้นทาง และการหลบเรือคุ้มกัน |
| **Toimaru / 問丸 และนายท่า/พ่อค้าส่ง** | คนกลางรับฝาก เก็บ ขน และจัดการสินค้าในตลาด/ท่า; เมืองท่าอาจมีสภาพ่อค้าและผู้คุมคลัง | รายละเอียดองค์กรของแต่ละท่าไม่เหมือนกัน | สร้างความสัมพันธ์สามชั้น: ผู้ผลิต–คนกลาง–ผู้คุ้มครอง และบันทึกหนี้/สัญญาแยกกัน |
| **Kaigōshū / 会合衆; Naya-shū / 納屋衆 ของ Sakai** | กลุ่มพ่อค้ามีอำนาจร่วมจัดการเมือง/ท่าและเชื่อมกับโกดัง การค้า งานเหล็ก อาวุธ และเรือ; Sakai เป็นกรณีเมืองท่าสำคัญ [5] [6] | อย่าทำให้ “พ่อค้าซาไก” เป็น NPC เดี่ยวหรือเป็นชนชั้นพ่อค้าแบบเดียวทั้งหมด | มี merchant council, warehouse houses, brokers, porters, smiths, pilots, guards และล่ามที่ผลประโยชน์ไม่ตรงกัน |
| **นายกองม้า / 馬廻・騎馬衆; ผู้ดูแลม้า** | นักรบม้าและผู้ดูแลม้าเป็นเครือข่ายทหาร/อุปถัมภ์; ผู้ดูแลคลังม้าและคนเลี้ยงม้าอาจมีสถานะต่ำกว่านักรบแต่สำคัญต่อสงคราม | `umamawari` เป็น horse guard/retainer ไม่ใช่ “กัปตันทหารม้า” ทุกกรณี; ตัวเลขม้าต้องมีหลักฐานเฉพาะ | แยก horse owner, groom, mounted retainer, cavalry leader; ฤดูกาล/อาหารสัตว์และเส้นทางสำคัญกว่าค่าพลัง |
| **Foot commander / 足軽大将** | นายกองทหารราบอาจเลื่อนสถานะจากนักรบท้องถิ่นหรือผู้ใต้บังคับบัญชาที่พิสูจน์ตัวเองได้; งานของ Kyoto Tachibana แสดงเส้นทางการเลื่อนฐานะของตระกูลชนบทในช่วงต่อเนื่อง [2] | อย่าย้อนเรื่องราวคนใดคนหนึ่งไปเป็นรูปแบบสากลของทุกกองทัพ | ใช้เป็น NPC ที่ต้องจัดคน อาวุธ เสบียง และความไว้ใจระหว่างบ้าน ไม่ใช่เพียงหน่วยโจมตี |
| **ช่างตีเหล็ก/ช่างอาวุธ/ช่างไม้/ช่างก่อสร้าง** | อยู่ภายใต้การอุปถัมภ์ของเมือง วัด พ่อค้า หรือเจ้าแคว้น; ผลิต ซ่อม และประเมินอาวุธ/สิ่งก่อสร้าง | ชื่อสำนักและคุณภาพสินค้าต้องผูกกับพื้นที่และช่วงเวลา | วัตถุดิบ/คำสั่งซื้อ/การคุ้มครองสร้าง faction ย่อย; ช่างรู้ข่าวจากการรับงานแต่ไม่รู้การเมืองทั้งหมด |
| **ชาวนา/ผู้เช่าที่/แรงงานไร้ที่ดิน/ชาวประมง** | ไม่ใช่กลุ่มเดียวกัน มีผู้ถือที่นา ผู้เช่า แรงงานตามฤดูกาล ชาวนาในหมู่บ้านรวมตัว และคนทำประมง/ป่า/เกลือ | หลักฐานชนชั้นล่างมักผ่านภาษี คดี และการเกณฑ์ จึงสรุปชีวิตส่วนตัวกว้างเกินไม่ได้ [7] | ให้มี collective bargaining, การหลบหนี, การซ่อนเสบียง, การอพยพ และความทรงจำของการปล้น/ช่วยเหลือ |
| **นักบวชชั้นผู้น้อย/ยามาบุชิ/ผู้ประกอบพิธี** | วัดและศาลเจ้าถือทรัพยากร เป็นที่ประชุม ผู้คุ้มครอง เอกสาร ผู้รักษา และผู้ส่งข่าว; ยามาบุชิมีความรู้ภูเขา/สมุนไพรในบางเครือข่าย [4] | ไม่ใช่พระทุกคนเป็นนักรบหรือผู้ใช้เวทมนตร์; บทบาทขึ้นกับวัดและยุค | แยกนักบวชพิธี ผู้ดูแลคลัง ผู้คัดลอกเอกสาร ผู้รักษา และผู้เดินทางแจกยา/เครื่องราง |
| **แพทย์/หมอยา/ล่าม/คนเดินสาร** | เคลื่อนที่ข้ามเครือข่ายและมีข้อมูลจากการเดินทาง; แหล่งหลักฐานแตกต่างกันมาก | ไม่ควรสร้างใบรับรองวิชาชีพแบบสมัยใหม่หรือความสามารถสากล | ใช้เป็นตัวกลางของข่าว ความช่วยเหลือ และหนี้บุญคุณ พร้อม `knowledge_scope` จำกัด |

### 3.1 ลำดับชั้น NPC ที่เหมาะกับเมืองท่า Sakai

พ่อค้าซาไกไม่ควรถูกออกแบบเป็นพ่อค้าเดี่ยวที่ยืนขายของในตลาด แต่ควรเป็นเครือข่ายต่อไปนี้: ผู้ผลิตชนบทและชาวประมง → คนรวบรวม/นายหน้า → คนแบกหามและแรงงานคลัง → คนเรือ/船頭 → เจ้าของโกดังหรือ納屋衆 → 会合衆/กลุ่มพ่อค้าร่วมประชุม → ผู้คุ้มครองท่าและผู้เรียกภาษี → ลูกค้า เช่น วัด กองทัพ บ้านนักรบ และตลาด Kyoto

การเจรจาของผู้เล่นจึงต้องเลือกคนให้ถูกเรื่อง หากต้องการเรือ ให้คุยกับ船頭หรือเจ้าของเรือ หากต้องการปล่อยสินค้า ให้คุยกับคนกลาง/โกดัง หากต้องการให้เมืองยอมรับ ให้เข้าหา会合衆 หากต้องการลดการตรวจ ให้หาผู้คุ้มครองหรือสร้างพยาน ความสัมพันธ์ระหว่างกลุ่มนี้อาจร่วมมือกันเมื่อท่าปลอดภัยและสินค้าไหลดี แต่แข่งขันกันเรื่องค่าคุ้มกัน สิทธิคลัง ส่วย และการรักษาอำนาจปกครองตนเอง [5] [6]

## 4. โครงสร้าง faction จริงและแบบจำลองความสัมพันธ์

### 4.1 หลักการสร้าง faction graph

ทุกแคว้นควรมีอย่างน้อยสี่ชั้น ได้แก่ **ผู้ถือความชอบธรรม**, **ผู้ถือกำลัง**, **ผู้ถือทรัพยากร**, และ **ผู้ถือข้อมูล/การเดินทาง** ฝ่ายหนึ่งอาจอยู่ได้มากกว่าหนึ่งชั้น เช่น วัดถือที่ดิน เอกสาร เครือข่ายผู้ศรัทธา และปราการ หรือสภาพ่อค้าถือคลัง เรือ เงินกู้ และข่าวจากท่าเรือ

สถานะ faction ไม่ควรเป็นมิตร/ศัตรูแบบถาวร แต่ควรมีเหตุผลของความสัมพันธ์ ได้แก่ ปกป้องเส้นทาง, แลกเสบียง, รักษาอิสระ, ลดภาษี, คุมท่า, แก้แค้น, รักษาหน้า, ต่อต้านศาสนาอื่น, หรือแย่งสิทธิในที่ดิน ตารางต่อไปเป็นโครงสร้างที่นำไปใส่ฐานข้อมูลได้

| เครือข่ายกรณีศึกษา | ร่วมมือได้เมื่อ | ขัดแย้งเมื่อ | NPC ชั้นกลางที่เป็นตัวเชื่อม |
|---|---|---|---|
| **Sakai/Izumi**: 会合衆・納屋衆, ช่าง, คนเรือ, วัด, Miyoshi/Oda, ผู้คุ้มครอง | ท่าปลอดภัย ได้กำไร รักษาสิทธิเมือง และมีเอกสาร/ของกำนัลเหมาะสม | เรียกส่วย ปิดท่า ยึดโกดัง บังคับส่งอาวุธ หรือทำให้ศักดิ์ศรีเมืองเสีย | นายท่า คนกลาง โกดัง ล่าม เสมียนภาษี ช่างเหล็ก |
| **Hine Estate/ชุมชนอาณาเขต** | ผู้ปกครองรับรองสิทธิหมู่บ้าน ปกป้องน้ำ/นา และไม่เก็บซ้ำซ้อน | ผู้คุมใหม่เรียกภาษีซ้ำ ใช้แรงงานเกิน หรือขัดสิทธิเอกสารเดิม | ผู้ดูแลอาณาเขต ผู้ใหญ่หมู่บ้าน คนตรวจบัญชี นักบวช |
| **Kaga Ikkō** | ชุมชน วัด และนักรบท้องถิ่นเห็นว่าภัยร่วมกันคุกคามศรัทธา/สิทธิ | ไดเมียวภายนอกพยายามยุบเครือข่าย เก็บส่วย หรือยึดวัด | พระผู้ดูแลวัด ผู้นำหมู่บ้าน นักรบ地侍 พ่อค้าเสบียง |
| **Iga/Kōka**: 地侍, 惣, ศาลเจ้า, เครือญาติ | ศัตรูภายนอกคุกคาม自治 และมีการแบ่งงาน/ข่าว/เส้นทางที่ยุติธรรม [3] [4] | ผู้ครองภายนอกตั้งป้อม เรียกตัวประกัน หรือบังคับให้ยอมเป็นข้าราชบริพาร | ผู้ใหญ่เครือญาติ ผู้ส่งข่าว นักนำทาง นักบวชภูเขา |
| **Kai/Takeda** | รัฐให้รางวัลและปกป้องสิทธิของผู้คุมม้า เหมือง ป่า และด่าน; เสบียงไปถึง | ขาดเกลือ ขาดม้า คำสั่งจากบ้านขัดกัน หรือการเกณฑ์ทำลายหมู่บ้าน | เสมียนคลังม้า คนเลี้ยงม้า นายด่าน คนขนเกลือ ผู้ดูแลเหมือง |
| **Ōmi**: Rokkaku/Azai/Oda, ท่า Biwa, วัด | ใครคุมด่าน/เรือให้ความปลอดภัยและไม่เรียกค่าผ่านทางซ้ำ | สงครามแย่งทะเลสาบ ทางผ่าน และคลัง; ฝ่ายท้องถิ่นถูกบังคับเลือกข้าง | นายเรือ คนเก็บค่าผ่านทาง นักบวช/ผู้คุมท่า พ่อค้าข้าว |
| **Kantō/Hōjō** | ผู้ครองรับรองสิทธิ kokujin คุมโจร/ถนน และทำให้ตลาดทำงาน | การแย่งที่ดิน เปลี่ยนพันธมิตร การประเมินที่ดินใหม่ หรือปิดตลาด | ผู้ดูแลด่าน ผู้ใหญ่หมู่บ้าน เจ้าของม้า พ่อค้าตลาดหกวัน |
| **Mōri/Inland Sea** | ท่าเรือได้รับคุ้มกัน เรือมีงาน และเมืองได้รับส่วนแบ่ง | แย่งค่าผ่านทาง โจรสลัด/กองเรือคู่แข่ง หรือบังคับท่าให้ส่งข่าว | 船頭 นายท่า นักนำร่อง คนเก็บคลัง ผู้คุมปราสาท |
| **Hakata/Hizen** | พ่อค้า ท่า และผู้ปกครองแบ่งผลประโยชน์ มีล่ามและกฎท่า | ยึดท่า ปิดการค้าต่างชาติ เปลี่ยนผู้คุ้มครอง หรือแข่งขันระหว่างผู้มีสิทธิ | ล่าม นายหน้า นายท่า เสมียนคลัง พ่อค้าจีน/โปรตุเกส |
| **Satsuma/Ryūkyū network** | เส้นทางทะเลปลอดภัย สินค้าเฉพาะทางทำกำไร และผู้ปกครองรักษาความสัมพันธ์ | คุมเกาะ/ช่องแคบ เรียกเรือเข้าระบบทหาร หรือแย่งสินค้านำเข้า | คนเรือ ผู้แปลภาษา พ่อค้าเกาะ ผู้ดูแลคลัง Shimazu |

**คำเตือน:** ตารางนี้เป็น faction model สำหรับกรณีศึกษา ไม่ใช่รายชื่อ “ฝ่ายทั้งหมด” ที่มีอยู่พร้อมกันทุกปี ความสัมพันธ์ต้องติด `valid_from`, `valid_to` และ `provenance` เสมอ

## 5. ปฏิทิน Sengoku และ Seasonal Pressure

### 5.1 ปฏิทิน

ญี่ปุ่นยุค Sengoku ใช้ปฏิทินจันทรสุริยคติที่รับอิทธิพลจากจีนผ่านคาบสมุทรเกาหลีและปรับเดือนอธิกสุรทินให้สอดคล้องกับฤดูกาล [1] ดังนั้นวันที่ในเอกสารเก่าต้องเก็บเป็น `calendar_system`, `era_name`, `lunar_month`, `day` และวันที่แปลงแบบ Gregorian ที่อาจมีความไม่แน่นอน ไม่ควรแสดงว่า “เดือน 5” เท่ากับพฤษภาคมเสมอ

| ช่วงโดยประมาณในปีเกษตร | งานและแรงงาน | ผลต่อการรบ/เสบียง | ตัวแปรเกม |
|---|---|---|---|
| ปลายหนาว–ต้นใบไม้ผลิ | ซ่อมคันนา เตรียมเมล็ด ไถ/เตรียมพื้นที่; Hokuriku และภูเขาอาจยังมีหิมะ | ถนนภูเขายาก การขนของช้า แต่บางพื้นที่รบได้ก่อนงานนาหนัก | `road_condition`, `labor_availability`, `snow_risk` |
| ฤดูปลูก/ต้นฤดูฝน | เพาะกล้า ดำนา กำจัดวัชพืช งานใช้แรงงานครัวเรือนสูง | การเกณฑ์คนชนบทมีต้นทุนทางการเมืองสูง ฝนทำให้แม่น้ำสูงและเส้นทางโคลน | `crop_phase=transplanting`, `labor_pressure`, `river_level`, `disease_risk` |
| ฤดูร้อน | ดูแลนา ตัดหญ้า เก็บของป่า/ทะเลตามพื้นที่ | ความร้อน โรค น้ำหลาก และฝนทำให้ล้อม/ขนส่งเสี่ยง; เรือมีลม/คลื่นและพายุเฉพาะภูมิภาค | `heat`, `flood`, `sea_state`, `food_spoilage` |
| ปลายฤดูร้อน–ต้นใบไม้ร่วง | เก็บเกี่ยวข้าวเร็ว/กลาง/ช้าไม่พร้อมกันทุกพื้นที่ | กองทัพต้องเลือกระหว่างรอผลผลิตกับโจมตีก่อนศัตรู; หลังเก็บเกี่ยวเสบียงเพิ่มแต่แรงงานอาจยังยุ่ง | `crop_phase=harvest`, `food_stock`, `market_pressure` |
| กลาง–ปลายใบไม้ร่วง | นวด เก็บ คัด และส่งส่วย; จัดคลังและซ่อมเครื่องมือ | หน้าต่างเสบียงดีขึ้นในบางพื้นที่ แต่ด่าน/ทะเล/หิมะเริ่มจำกัด | `stock_replenishment`, `route_reliability`, `tax_due` |
| ฤดูหนาว | ซ่อมบ้าน/เครื่องมือ งานป่า การปั่น/ทอ และพิธี; หิมะ/ทะเลต่างกันมาก | ภูมิภาคอุ่นอาจยังเดินทัพได้ ขณะที่ Hokuriku และด่านภูเขาอาจชะลอ; ไม่ควรตั้งกฎว่า “ฤดูหนาวไม่มีสงคราม” | `snow`, `road_closure`, `labor_slack`, `campaign_window` |

### 5.2 ตัวปรับภูมิภาค

Hokuriku เช่น Echizen, Kaga, Noto และ Echigo ควรมี snow/road pressure สูงกว่าภาค Kinai ในหลายช่วง ขณะที่ Inland Sea, Sakai, Hizen และ Satsuma ต้องใช้ `sea_state`, ลมตามฤดูกาล น้ำขึ้นลง และพายุเป็นตัวแปรแยกจากฝนบนบก Kai, Hida, Shinano, Tamba และ Iga/Kōka ควรใช้ความสูงและ snow pass แยกกัน ไม่ใช้ “อากาศญี่ปุ่น” ค่าเดียว

ฤดูกาลไม่ควรบอกว่ากองทัพ “ห้าม” ทำสิ่งใด แต่บอกต้นทุนและทางเลือก ผู้เล่นอาจออกทัพช่วงงานนาได้ถ้ามีกำลังประจำหรือเกณฑ์แรงงานจากพื้นที่อื่น แต่จะเสียชื่อเสียง/เสบียง/ความสามารถในการเก็บภาษี การรอเก็บเกี่ยวอาจทำให้กองทัพถูกเสริมกำลัง การออกเรือช่วงตลาดราคาสูงอาจคุ้มค่าแต่เสี่ยงพายุ และการปิดด่านอาจทำให้เส้นทางภูเขาปลอดภัยจากศัตรูแต่ทำให้ราคาข้าวพุ่ง

## 6. เศรษฐกิจจริง: ข้าวไหลอย่างไร และใครคุมเส้นทาง

### 6.1 โซ่การไหลของข้าวและสินค้า

แบบจำลองที่เหมาะสมไม่ใช่ “ชาวนา → ไดเมียว” เส้นเดียว แต่เป็นเครือข่าย: ครัวเรือน/ผู้ผลิต → ผู้ใหญ่หมู่บ้านหรือผู้ดูแลอาณาเขต → ผู้รับส่วย/ผู้ถือสิทธิ → คลังท้องถิ่นหรือปราสาท → ตลาด/ท่า → กองทัพ วัด เมือง และผู้บริโภค การไหลบางส่วนถูกแปลงเป็นเงินหรือสินค้าอื่นก่อนถึงคลัง

ประวัติศาสตร์จังหวัด Fukui ย้ำว่าเอกสารที่อธิบายรายละเอียดภาษีระดับ所領ในยุคสงครามมีน้อย แต่ตัวอย่าง ค.ศ. 1551/天文20 แสดงการเก็บ年貢米, 地子銭, 段銭 และ公事 โดยผู้ปกครองท้องถิ่น/ผู้ใต้บังคับบัญชาของ Takeda เป็นผู้รับโดยตรง อีกกรณีมี海産物จาก浦ส่งเป็นส่วย [7] นี่สนับสนุนให้เกมมีทั้งภาษีข้าว เงิน งานบริการ และสินค้าทะเล โดยไม่ทำให้การปกครองเป็นระบบเดียวทั่วประเทศ

งานวิชาการภาษาญี่ปุ่นเกี่ยวกับดินแดน Hōjō กล่าวถึง六斎市เป็นตลาดที่ชาวนาใช้เปลี่ยนธัญพืชเป็นเงิน และเชื่อมกับนโยบายเหรียญ/撰銭ของ Hōjō [8] ในเชิงระบบ นี่หมายความว่าตลาดไม่ได้เป็นเพียงที่ซื้อของ แต่เป็นเครื่องมือที่ผู้ปกครองพยายามทำให้ผลผลิตกลายเป็นเงินและควบคุมการหมุนเวียน

### 6.2 ปัจจัยเปลี่ยนราคา

| ปัจจัย | ผลต่อสินค้า/ราคา | ผู้เล่นที่ได้อำนาจ |
|---|---|---|
| ฤดูเก็บเกี่ยว | หลังเก็บเกี่ยวข้าวมีมากขึ้นในพื้นที่นั้น แต่ต้นทุนขนและภาษียังต่างกัน | ผู้ถือคลัง ผู้ซื้อข้าวล่วงหน้า พ่อค้าส่ง |
| สงคราม/การล้อม | ความต้องการข้าว เกลือ ม้า เหล็ก เชือก ไม้ และเรือเพิ่ม; เส้นทางถูกตัด | กองทัพ ผู้คุมด่าน ผู้คุ้มกัน พ่อค้าเสี่ยง |
| ฝน น้ำหลาก หิมะ | ขนส่งช้าหรือหยุด สินค้าเสีย ค่าคุ้มกันสูง | นายเรือ นายด่าน เจ้าของคลัง |
| เหรียญและการแลกเงิน | เหรียญต่างคุณภาพ/ขาดแคลนทำให้คนไม่รับหรือคิดส่วนลด; ตลาดที่ผู้ปกครองรับรองเงินได้เปรียบ | เจ้าแคว้น ตลาดที่มีอำนาจ และ money changers |
| ภาษี/ค่าผ่านทาง | สินค้าถึงปลายทางแพงขึ้น เส้นทางอ้อมอาจคุ้มกว่า | ผู้ถือด่าน วัด เจ้าเมือง พ่อค้าเมืองท่า |
| ความปลอดภัย/โจรสลัด | ค่าคุ้มกันและการสูญหายเพิ่ม แต่ผู้คุมทางมีรายได้ | กองเรือคุ้มกัน กลุ่มท้องถิ่น นายท่า |
| อุปสงค์จากเมือง/วัด/กองทัพ | สินค้าช่าง อาวุธ กระดาษ สุรา ปลาแห้ง และผ้าราคาดีในตลาดบางแห่ง | ช่างที่มีสัญญา พ่อค้าโกดัง ผู้มีเครดิต |

**สิ่งที่ยังไม่ควรทำ:** ไม่ควรกำหนดว่าข้าว 1 หน่วยมีราคาตายตัวทั่วญี่ปุ่น หรือแปลงหน่วยเงินโบราณเป็นค่าเงินปัจจุบันโดยตรง หากไม่มีบัญชีของพื้นที่/ปีนั้น ให้ใช้ “ช่วงราคาเชิงเกม” พร้อม `price_basis`, `season`, `market_id`, `confidence` และเหตุผลการเปลี่ยนแปลง

## 7. เปรียบเทียบระบบเกม

### 7.1 Blades in the Dark

เอกสาร SRD ทางการแยก **faction status** เป็นค่าของแต่ละฝ่ายตั้งแต่ -3 ถึง +3 ตั้งแต่ Allies, Friendly, Helpful, Neutral, Interfering, Hostile ถึง War การปฏิบัติการอาจเพิ่ม status กับฝ่ายที่ช่วยและลด status กับฝ่ายที่ได้รับผลกระทบ [9] หน้า Heat ทางการแยก exposure ของปฏิบัติการออกจาก Wanted level และเมื่อ Heat สะสมถึง threshold จะเกิด Wanted level; Wanted ที่สูงขึ้นทำให้การตอบสนองของ law enforcement รุนแรงขึ้น [10] หลังภารกิจยังมี Entanglements ที่เปลี่ยนผลกระทบให้กลายเป็นปัญหาที่ต้องเล่นต่อ ไม่ใช่แค่ลบคะแนน [11]

สิ่งที่ควรยืมคือการแยกชื่อเสียงตามฝ่าย, การทำให้สถานะเปลี่ยนจากผลกระทบที่สังเกตได้, และการใช้ consequence หลังภารกิจ สิ่งที่ต้องเปลี่ยนคือ Sengoku ต้องมี scope จังหวัด/เมือง/ด่าน, ความเร็วข่าว, คุณภาพพยาน และความแตกต่างระหว่าง “ฝ่ายรู้” กับ “โลกเกิดขึ้นจริง” จึงไม่ควรใช้ Heat ค่าเดียวทั้งประเทศ

### 7.2 Pendragon

Chaosium อธิบาย Pendragon ว่าใช้ Traits และ Passions ให้รางวัลกับการกระทำตามคุณธรรมและการแข่งขันเพื่อ Glory อีกทั้งผูกการผจญภัยเข้ากับฤดูกาล และเปิดให้แคมเปญเดินต่อผ่านลูกหลานของตัวละคร [12] สิ่งที่เหมาะกับ Sengoku คือการมี phase เปลี่ยนฤดูกาล/ปี, ผลสะสมต่อครอบครัว/ชื่อบ้าน, และความตึงเครียดระหว่างอุดมคติกับการอยู่รอด แต่ไม่ควรนำรหัสอัศวินหรือค่าเกียรติสากลมาแทน faction reputation หลายฝ่าย

### 7.3 Open-world NPC memory และสิ่งที่ควรระวัง

สิทธิบัตร Nemesis ที่เผยแพร่สาธารณะอธิบายแนวคิด NPC ที่มีตัวตนต่อเนื่อง อยู่ใน hierarchy ของ faction และมีความสัมพันธ์เฉพาะบุคคลระหว่าง rank/traits กับเหตุการณ์ รวมถึงตัวอย่าง overlord–warchief–captain–soldier [13] สิ่งที่ยืมได้ในระดับ pattern คือ stable identity, hierarchy, persistent relationship, event-triggered return และการรวมระดับ NPC กับ faction

อย่างไรก็ตาม ไม่ควรคัดลอก claim หรือ presentation เฉพาะของระบบนั้นโดยตรง สิ่งที่ Sengoku ควรทำต่างคือเก็บ memory แบบ fact/belief/rumor/unknown, ขอบเขตพยาน, เวลาเดินทางของข่าว และสิทธิการเห็นข้อมูล ใช้ hierarchy ที่เป็น household/retainer/port/village league ตามประวัติศาสตร์ของเกม ไม่ใช้โครงสร้าง overlord–captain แบบแฟนตาซี การใช้แนวคิดในเชิงพัฒนาเชิงพาณิชย์ควรให้ผู้เชี่ยวชาญตรวจ IP แยกต่างหาก

## 8. ข้อเสนอ Reputation, Heat/Wanted และ Seasonal Pressure

### 8.1 Reputation: edge ไม่ใช่คะแนนเดียว

เก็บความสัมพันธ์ระหว่างผู้เล่น/actor กับ faction หรือชุมชนเป็น edge ที่มีแกนภายใน `trust`, `respect`, `fear`, `debt`, `resentment` และ `reliability` ค่าภายในเป็นตัวเลขสำหรับคำนวณ แต่ UI แสดงคำอธิบาย เช่น “ยอมเจรจาแต่ไม่ให้เข้าคลัง”, “ชาวบ้านช่วยซ่อนตัว”, หรือ “ซามูไรเฝ้าดูทุกคำพูด”

การเปลี่ยนค่าเกิดจาก event ซึ่งบันทึกการกระทำ เป้าหมาย ผลกระทบ พยาน หลักฐาน สถานที่ เวลา และการตีความของ faction หากช่วยหมู่บ้านโดยไม่มีคนเห็น อาจเพิ่ม debt กับครัวเรือนเดียว แต่ไม่เพิ่มชื่อเสียงกับทั้งจังหวัด หากช่วยพ่อค้าซาไกแต่ทำให้ข้าวขาดในหมู่บ้าน ชื่อเสียงกับ merchant council อาจเพิ่ม ขณะที่ trust ของชาวบ้านลด

**กฎเกมที่เป็นข้อเสนอ ไม่ใช่ข้อเท็จจริงประวัติศาสตร์:** ใช้ internal range -100 ถึง +100, clamp การเปลี่ยนครั้งเดียว, decay เฉพาะค่าที่เหมาะกับการลืม เช่น ข่าวลือเสื่อมเร็วกว่า debt และ resentment ที่มีเอกสาร/พยานไม่เสื่อมเอง ให้ทุก delta อธิบายย้อนกลับไปยัง source event

### 8.2 Heat/Wanted: ความร้อนหลายขอบเขต

เก็บอย่างน้อย `local_heat` ระดับหมู่บ้าน/เมือง/ด่าน, `province_heat` ระดับแคว้น และ `faction_alert` ของฝ่ายผู้ตามหา แยกองค์ประกอบ `incident_severity`, `witness_count`, `evidence_strength`, `identity_confidence`, `communication_speed`, `search_budget`, `border_control` และ `political_priority` ออกจากกัน

วงจรเหตุการณ์คือ `unseen → suspected → identified → wanted → archived` แต่สถานะอาจลดเมื่อพยานถูกหักล้าง หลักฐานเสีย ผู้คุ้มครองเปลี่ยน หรือสงครามใหญ่กว่ากลบความสนใจ เหตุการณ์ที่อยู่ในเอกสาร/คำสั่งไม่ควรถูกลบโดยสมบูรณ์ เพียงเปลี่ยนจากการไล่ล่าเป็นหมายเก่า ข่าวลือ หรืออุปสรรคเมื่อแสดงตัว

วิธีลด Heat ต้องเป็นทางเลือกที่สร้างผลข้างเคียง ได้แก่ เปลี่ยนเส้นทาง, ใช้ใบผ่านทาง, ยอมชดใช้, สร้างพยาน, เปลี่ยนชื่อ/เครื่องแต่งกาย, ยอมถูกสอบสวน, ช่วยผู้คุมด่าน หรือส่งมอบข้อมูลของฝ่ายอื่น วิธีปลอมเอกสารอาจลด local_heat ชั่วคราวแต่เพิ่ม evidence และ faction_alert หากถูกเปิดโปง

### 8.3 Seasonal Pressure: state ระดับแคว้นและเส้นทาง

คำนวณ `crop_phase`, `food_stock`, `labor_availability`, `road_condition`, `river_level`, `sea_state`, `disease_risk`, `war_readiness` และ `market_pressure` แยกในแต่ละ province/route ไม่ใช้ฤดูกาลเดียวกับทุกพื้นที่ อัปเดตเมื่อเปลี่ยนเดือน/เหตุการณ์สำคัญ ไม่คำนวณสภาพโลกใหม่ทุก frame

ผู้เล่นต้องเห็นผลสั้น ๆ ก่อนตัดสินใจ เช่น “เส้นทาง Kōshū มีหิมะสูง; ใช้เรืออ้อมได้แต่ข่าวสารช้าลง” หรือ “หมู่บ้านกำลังเกี่ยวข้าว; จ้างคนได้ยากแต่ซื้อข้าวล่วงหน้าได้ถูกกว่า” ข้อความควรบอกเหตุผลและทางเลือก ไม่เพียงขึ้นสัญลักษณ์ debuff

## 9. UI/UX: ช่องเดิมหรือเมนูใหญ่

### 9.1 สิ่งที่อยู่ในช่องเดิม

ในหน้าสนทนาให้แสดง faction ที่กำลังคุยด้วยพร้อม stance, สิ่งที่ฝ่ายนั้นรู้ และสิ่งที่ต้องการ ใน HUD ให้แสดงเดือน/ฤดูกาล, local_heat แบบคำสั้น, และ seasonal pressure ของเส้นทางปัจจุบัน ในหน้าแคว้นให้แสดงผู้ปกครองปัจจุบัน, faction ที่ผู้เล่นเคยพบ, เส้นทางที่ปลอดภัย/เสี่ยง และราคาสินค้าหลักที่มีหลักฐาน/ความเชื่อมั่น

### 9.2 เมนูใหญ่เดียว: Power & Rumor Network

| แท็บ | สิ่งที่เห็น | สิ่งที่ไม่ควรเปิดทั้งหมด |
|---|---|---|
| แผนที่อำนาจ | faction ที่ตัวละครรู้จัก, ผู้คุ้มครอง, ด่าน, เส้นทาง | ค่า secret faction ที่ตัวละครไม่เคยรู้ |
| ความสัมพันธ์ | trust/respect/fear/debt/resentment ของฝ่ายที่พบ พร้อมเหตุการณ์อ้างอิง | ความคิดลับของ NPC ที่ไม่มีหลักฐาน |
| ความเสี่ยง | heat ของพื้นที่ที่ผู้เล่นเคยมีข่าวหรือมีช่องทางข่าว | Heat ที่ผู้เล่นไม่มีเหตุผลจะรู้ |
| ตลาดและเสบียง | สินค้า เส้นทาง สถานะฤดูกาล และช่วงราคา | ราคาที่เป็นตัวเลขแน่นอนหากข้อมูลเป็นเพียงข่าวลือ |
| บันทึกเหตุการณ์ | สิ่งที่ตัวละครจำได้ ใครเป็นพยาน และข่าวที่ขัดกัน | hidden_truth ของ GM |

หลักการคือเมนูใหญ่มีไว้ **วางแผน** ไม่ใช่เป็นกล้องวงจรปิดของโลก ตัวละครชาวบ้านกับผู้เล่นที่มีสายข่าวใน Sakai ควรเห็นคนละข้อมูล

## 10. ลูปการเล่น

### ลูปสั้นในฉาก

ผู้เล่นกระทำ → ระบบประเมินพยาน/หลักฐาน → faction ตีความ → reputation/heat เปลี่ยนเฉพาะ scope ที่ได้รับผล → NPC ตอบสนอง → ผู้เล่นได้รับข้อมูลไม่ครบ → เลือกแก้สถานการณ์ต่อ ลูปควรจบในเวลาไม่กี่นาทีของการเล่นเพื่อให้เห็นความสัมพันธ์ระหว่างการกระทำกับผล

### ลูประยะกลางในแคว้น

ผู้เล่นเลือกเส้นทางและผู้คุ้มครอง → ฤดูกาลเปลี่ยนต้นทุน → reputation เปิดหรือปิดทางเลือก → heat เปลี่ยนระดับการตรวจ → ผู้เล่นชำระหนี้ เปลี่ยน faction หรืออ้อมทาง → ข่าวลือกระจายและตลาดปรับ → เกิดเหตุการณ์ตอบสนองที่ไม่ใช่แค่การต่อสู้

### ลูประยะยาว

เหตุการณ์สะสม → faction เปลี่ยนนโยบาย/พันธมิตร → เส้นทางสินค้าและเสบียงเปลี่ยน → ผู้เล่นต้องเลือกรักษาชื่อเสียงกับฝ่ายใด → ฤดูกาล/ผู้ปกครองใหม่เปลี่ยนความหมายของหนี้และหมายจับเก่า → NPC รุ่นถัดไปได้รับความทรงจำระดับบ้านหรือชุมชนที่ถูกคัดเลือก ไม่ใช่จำทุกอย่าง

### ฉากทดสอบหลัก

1. ผู้เล่นขนข้าวช่วยชาวบ้านในฤดูฝนโดยไม่จ่ายส่วย: ชาวบ้านเพิ่ม debt/trust แต่ผู้คุมด่านเพิ่ม suspicion และเจ้าแคว้นเพิ่ม alert เมื่อพบตราปลอม
2. ผู้เล่นถูกหมายจับใน Sakai แต่ยังไม่เป็นที่รู้จักใน Kai: ใช้คนกลาง/ใบผ่านทางช่วยได้ แต่หากต้นทางสืบพบจะมี communication event ตามมา
3. โรนินขอเข้าสังกัด: ผู้เล่นซื้อทักษะและข่าวของเขาได้ แต่ faction อื่นลด respect หากรับคนที่มีหนี้/ศัตรูไม่ทราบที่มา
4. shinobi นำข่าวที่ยังไม่ยืนยัน: ใช้เป็น rumor ได้แต่ห้ามป้อนเป็น fact ให้ AI; การตัดสินใจผิดอาจเปลี่ยน reputation และเปิดเส้นเรื่อง
5. พ่อค้าซาไกพบเรือคู่แข่งช่วงทะเลเสี่ยง: เลือกทำกำไรเร็ว คุ้มกัน หรือรอฤดูปลอดภัย แต่แต่ละทางกระทบ debt, market pressure และ heat ต่างกัน
6. กองทัพต้องการเกณฑ์คนช่วงเกี่ยวข้าว: ระดมกำลังทันทีได้แต่เพิ่ม resentment/food shortage; รอเก็บเกี่ยวช้ากว่าแต่เสบียงและชื่อเสียงดีขึ้น

## 11. สถาปัตยกรรมหลังบ้าน

ใช้ **event-sourced projection**: `event_log` เป็น source of truth แบบ append-only; `world_snapshot`, `heat_tracks`, `relationships`, `seasonal_states`, `markets` และ `context_summaries` เป็น projection ที่สร้างใหม่ได้ การแก้สูตรคำนวณจึงไม่ลบประวัติเดิม

| Store/Projection | หน้าที่ | ข้อมูลสำคัญ |
|---|---|---|
| `world_snapshot` | ค่าปัจจุบันสำหรับโหลดฉาก | run/date/season/current province/active routes |
| `factions` | identity และ policy | interests/resources/hierarchy/known regions |
| `relationships` | edge ระหว่าง actor/faction/NPC | scores, stance, scope, source events |
| `incidents` | เหตุการณ์ที่ทำให้เกิดชื่อเสียงหรือ Heat | witnesses/evidence/identity/visibility |
| `heat_tracks` | heat แยกพื้นที่และฝ่าย | local/province/faction status + transition history |
| `seasonal_states` | สภาพเดือน/เส้นทาง/แคว้น | crop/road/river/sea/food/labor/disease |
| `markets` | สินค้า คลัง ราคา และเส้นทาง | item/market/stock/price band/trend/provenance |
| `npc_memories` | ความจำและความเชื่อราย NPC | memory_type/salience/confidence/privacy/decay |
| `event_log` | replay, audit, rollback | event type/payload/occurred_at/causes |
| `context_summaries` | สรุปพร้อมส่ง AI | scope/time window/summary/source ids/token estimate |

เมื่อใช้ PostgreSQL ให้เก็บรายละเอียด flexible ใน `jsonb` และทำ projection/ตารางหรือ expression index สำหรับข้อมูลที่ query บ่อย เอกสาร PostgreSQL ระบุว่า `jsonb` เป็นรูปแบบแยกโครงสร้างที่ประมวลผลและทำ index ได้ดีกว่า `json` แต่ไม่รักษาลำดับ key และ duplicate keys [14] ดังนั้นไม่ควรเก็บโลกทั้งหมดเป็น JSON ก้อนเดียวแล้ว scan ทุกฉาก

## 12. JSON Schema และ query/index strategy

ใช้ JSON Schema Draft 2020-12 ซึ่งเป็นรุ่นที่มี metaschema ทางการและรองรับการกำหนด vocabularies/refs สำหรับ schema ที่ซับซ้อน [15] ทุก record ต้องมี `schema_version`, stable ID, `valid_from/valid_to`, `confidence`, `provenance` และ `source_event_ids` เมื่อข้อมูลเป็นข้ออนุมานหรือข่าวลือ

ดัชนีที่เหมาะกับ query ร้อน ได้แก่ `(run_id, province_id, local_heat_level)`, `(run_id, faction_id, stance)`, `(subject_id, target_id, scope)`, `(actor_id, memory_type, salience DESC)`, `(province_id, season, market_pressure)`, `(event_type, occurred_at, province_id)` และ `(item_id, market_id)` หากค้นคำศัพท์/ข่าวลือจำนวนมาก ให้ใช้ full-text/BM25 หรือ vector index แยก ไม่เพิ่ม GIN ทุก field โดยไม่วัด query plan

### ตัวอย่าง query เชิงระบบ

```sql
-- ด่านในแคว้นปัจจุบันที่เสี่ยง แต่มี faction ที่ผู้เล่นไว้ใจ
SELECT gate_id, local_heat_level, inspection_policy
FROM gate_projection
WHERE run_id = :run
  AND province_id = :province
  AND local_heat_level >= 2
  AND exists (
    SELECT 1 FROM relationship_projection r
    WHERE r.run_id = :run
      AND r.subject_id = :player
      AND r.target_id = gate_projection.protecting_faction_id
      AND r.trust >= 40
  );

-- memories ที่ควรส่งให้ NPC โดยไม่ปนข่าวลือความเชื่อมั่นต่ำ
SELECT memory_id, memory_type, summary, confidence, source_event_ids
FROM npc_memory_projection
WHERE run_id = :run AND actor_id = :npc
  AND salience >= :threshold
  AND memory_type IN ('fact','belief','rumor')
ORDER BY salience DESC, updated_at DESC
LIMIT :k;
```

## 13. Context compression สำหรับ AI

อย่าส่ง `world_state` ทั้งก้อนให้ AI ทุกครั้ง ให้ทำ retrieval ตามฉากและสิทธิข้อมูลตามลำดับต่อไปนี้: ระบุ actor/player, province/settlement, time window, active factions และเป้าหมาย → ดึง canonical facts → ดึง current local state → ดึง top-k memories/rumors ที่ actor มีสิทธิรู้ → ดึง recent causal events → สร้าง summary ที่ใส่ provenance → deduplicate และตรวจ contradiction → ส่ง structured context ให้โมเดล

แบ่ง context เป็นห้าชั้น ได้แก่ **invariants**, **current scene**, **retrieved local facts**, **actor memory/beliefs**, และ **recent causal events** ใช้ token budget แยกกัน ถ้าฉากอยู่ที่ Sakai ให้ดึง Sakai/Izumi และเส้นทางที่ติดกันก่อน ไม่ดึง 66 แคว้นทั้งหมด

บทความ Contextual Retrieval ของ Anthropic เสนอการเติมบริบทเฉพาะ chunk ก่อนสร้าง contextual embeddings และ contextual BM25 พร้อม reranking; บทความรายงานผลการทดลองว่าลด failed retrieval ได้ 49% และเมื่อรวม reranking 67% [16] ในเกม ให้เติม `province_id`, `settlement_id`, `time window`, `faction`, `event type` และระดับหลักฐานลงใน chunk ก่อน index เพื่อไม่ให้ข้อความ “เขาเพิ่ม 3%” ถูกตัดขาดจากว่าใคร/ที่ไหน/เมื่อใด

### Memory policy

| ชนิด | ความหมาย | อายุ/การเสื่อม |
|---|---|---|
| `fact` | เหตุการณ์ที่ actor เห็น/เอกสารที่ยืนยันในขอบเขตของเขา | ไม่ลบถ้ามีหลักฐาน; อาจถูกแก้ด้วย contradiction ที่มี provenance |
| `belief` | การตีความส่วนตัว | เสื่อม/เปลี่ยนจากประสบการณ์ใหม่ |
| `rumor` | ข่าวจากคนอื่น ยังไม่ยืนยัน | เสื่อมเร็ว; confidence เพิ่มเมื่อมีพยานใหม่ |
| `unknown` | ช่องว่างที่ระบบห้ามเติม | คงเป็น unknown จนกว่าจะมี event/observation |

ใช้ rolling summary ระดับ NPC, faction, province และช่วงเวลา แต่เก็บ event สำคัญแบบย่อที่ผู้เล่นอาจอ้างกลับมาได้ ใช้ `contradiction_ledger` เมื่อข่าวสองสายไม่ตรงกัน และไม่ให้ AI เห็น `hidden_truth` หรือ memory ที่ผู้เล่นไม่มีสิทธิรู้

## 14. JSON Schema design ที่นำไปใช้ได้

ไฟล์ `sengoku_world_state.schema.json` ที่แนบมาคือ schema ฉบับเสนอสำหรับ snapshot และ event store โดยใช้ `$schema` ของ Draft 2020-12 กำหนด enum ของ `memory_type`, `heat_status`, `confidence_label`, `scope_type` และกำหนด required IDs/เวลา/provenance ส่วนไฟล์ตัวอย่างแสดงกรณีผู้เล่นใน Sakai ที่ชาวบ้านไว้ใจแต่สภาพ่อค้าระวัง และด่านเพิ่มการตรวจเพราะใบผ่านทางมีหลักฐานไม่แน่นอน

คำแนะนำสำคัญคือให้แยก `current_projection` กับ `event_log` ตั้งแต่แรก ถ้าฐานข้อมูลช่วงต้นยังใช้ไฟล์ JSON ให้แบ่งตาม run/province และสร้าง index ในหน่วยความจำจาก `(province_id, faction_id, actor_id, event_type)` เมื่อโตขึ้นให้ย้าย projection ที่ query บ่อยไป SQLite/PostgreSQL โดยคง JSON เป็น interchange/debug/export

## 15. สิ่งที่ควรทำและไม่ควรทำ

| ควรทำ | ไม่ควรทำ |
|---|---|
| แสดงเหตุผลของการเปลี่ยนชื่อเสียงและ Heat ผ่าน event/พยาน/หลักฐาน | เพิ่มหรือลด reputation เพราะผู้เล่นเดินผ่านพื้นที่เฉย ๆ โดยไม่มีเหตุผล |
| ให้ชาวบ้าน ซามูไร พ่อค้า และวัดมีการประเมินผู้เล่นคนละแบบ | ใช้ค่า morality เดียวเป็นชื่อเสียงของทั้งประเทศ |
| ทำ Heat เป็นพื้นที่/ฝ่ายและให้ทางแก้หลายแบบ | ทำให้ศัตรูทุกแคว้นรู้เหตุการณ์ทันที |
| ให้ฤดูกาลมีทั้งต้นทุนและโอกาส | ทำฤดูเป็น debuff หกเดือนหรือบังคับให้รออย่างเดียว |
| เก็บ event log และ provenance เพื่อ replay/แก้สูตร | เขียนทับประวัติเมื่อ projection เปลี่ยน |
| แยก fact/belief/rumor/unknown และ scope สิทธิ | ให้ AI เติมคำตอบจากช่องว่างประวัติศาสตร์เป็น fact |
| ใช้ศัพท์ญี่ปุ่นตามช่วงเวลาและติดป้ายความไม่แน่นอน | เรียกผู้สอดแนมทุกคนว่า ninja หรือเรียกผู้ใหญ่หมู่บ้านทุกยุคว่า shōya |
| ใช้ระบบ open-world เป็นแรงบันดาลใจระดับ pattern และตรวจ IP | คัดลอก hierarchy/presentation/claim ของระบบที่มีสิทธิบัตร |

## 16. แผนทดสอบก่อน integrate

ทดสอบ unit logic ของ reputation delta, witness scope, faction interpretation, heat transition, evidence decay, seasonal update, route closure, market pressure, memory retrieval, contradiction handling และ projection rebuild จาก event log

ทดสอบ integration scenario อย่างน้อยหกฉาก: ชาวบ้านรักแต่ซามูไรไม่ไว้ใจ; มีหมายจับใน Izumi แต่ไม่ใช่ Kai; ข่าวลือผิดจากพยานน้อย; ใบผ่านทางปลอม; การเดินทัพช่วงเกี่ยวข้าว; และเรือ Sakai เลือกระหว่างราคาสูงกับทะเลเสี่ยง ทดสอบด้วย seed เดียวกันเพื่อดูว่าเหตุผลของผลลัพธ์คงที่และตรวจย้อนกลับได้

ทดสอบสิทธิข้อมูลสามมุมมอง ได้แก่ player UI, NPC prompt และ GM/debug view ตรวจว่า NPC ไม่ได้รับ secret ของ faction อื่น ตัวละครไม่เห็นอนาคต และ AI ไม่เปลี่ยน `unknown` เป็น fact โดยไม่มี event สนับสนุน
