# Negotiation / Barter Conversation — Play UI (ระบบต่อรองและแลกเปลี่ยน)

Dust & Fire — ข้อเสนอ Design ขั้นต้น (Planned / [NOT FOUND])

> สถานะ: **ข้อเสนอเพื่อจัดเก็บและขออนุมัติเท่านั้น** ยังไม่แก้โค้ด, GameState, Local Save หรือกติกาที่ใช้งานจริง

## 1. หน้าที่ของระบบ

เพิ่มระบบต่อรองและแลกเปลี่ยนสินค้าโดยตรงเข้ามาใน **หน้า Play** เพื่อให้ผู้เล่นสามารถพูดคุยกับ NPC และเสนอราคา/สินค้าเองได้ โดยไม่จำเป็นต้องผ่านเมนูซื้อขายแบบเดิมทั้งหมด

## 2. Negotiation Panel

- เพิ่มปุ่ม/ช่อง **“Negotiate / ต่อรอง”** ภายในหน้า Play เมื่อผู้เล่นอยู่ในสถานการณ์ที่สามารถซื้อขายกับ NPC ได้
- เมื่อเปิดแล้ว ให้แสดง **conversation panel ขนาดกะทัดรัด** โดยยังมองเห็นฉากและสถานะของ Play อยู่

องค์ประกอบหลัก:

- **NPC Speaker**
  - ชื่อ NPC
  - สถานะ/อาชีพโดยย่อ
  - อารมณ์หรือท่าที เช่น Friendly / Neutral / Suspicious / Angry
- **Current Offer**
  - สินค้าที่กำลังซื้อหรือขาย
  - ราคาปัจจุบัน
  - ประเภทเงินที่ NPC ต้องการ
- **Player Offer**
  - จำนวนเงินที่เสนอ
  - สินค้าที่เสนอแลก
  - จำนวนสินค้า
- **Free-text Input**
  - ช่องให้ผู้เล่นพิมพ์ข้อเสนอด้วยคำพูดของตัวเอง
    - เช่น “ลดราคาให้ข้าหน่อย ถ้าซื้อสองเล่ม”
    - หรือ “ข้าไม่มีเงิน แต่มีข้าวอยู่สามกระสอบ”
- **Send / เสนอ**
  - ส่งข้อเสนอให้ NPC วิเคราะห์และตอบกลับ

## 3. Direct Barter UI

ผู้เล่นสามารถเลือก **แลกสินค้าโดยตรง โดยไม่ต้องใช้เงิน**

ตัวอย่าง UI:

- NPC ต้องการ: ข้าว 2 โคกุ
- ผู้เล่นเสนอ: เกลือ 1 กระสอบ / Mon 40

หรือสามารถพิมพ์ข้อเสนอเองผ่านช่องข้อความ เช่น:

> “ข้าให้เกลือสองถุง แลกกับข้าวหนึ่งโคกุ”

ระบบจะตีความข้อเสนอแล้วสร้าง transaction ที่เหมาะสม

## 4. Conversation Flow

UI ควรให้ความรู้สึกเหมือนกำลัง **ต่อรองกับคนจริง** มากกว่ากำลังกรอกฟอร์มร้านค้า

ตัวอย่าง:

- Player: “ดาบเล่มนี้ 800 Mon แพงไป ข้าให้ 600”
- NPC: “600? เจ้าคิดว่าข้าหาเหล็กมาจากไหนกัน?”

จากนั้นผู้เล่นสามารถตอบกลับได้อีกครั้ง หรือยอมรับข้อเสนอ ไม่ควรจำกัดผู้เล่นให้เลือก dialogue option ทุกครั้ง

## 5. Quick Actions

เพื่อไม่ให้ผู้เล่นต้องพิมพ์ทุกครั้ง ให้มีปุ่มลัดสำหรับข้อเสนอทั่วไป เช่น:

- Offer Lower Price
- Offer More Quantity
- Offer Item
- Offer Mixed Payment
- Accept
- Decline
- Walk Away

ปุ่มเหล่านี้เป็น **ทางเลือกเสริม** ส่วน Free-text Negotiation เป็นช่องทางหลักสำหรับผู้เล่นที่ต้องการควบคุมคำพูดเอง

## 6. Offer Preview

ก่อนส่งข้อเสนอ UI ควรแสดงสิ่งที่ผู้เล่นกำลังเสนออย่างชัดเจน:

- You Offer: 600 Mon / 1 Salt ×
- You Want: Iron Sword ×1

เพื่อป้องกันความเข้าใจผิดและลดการทำธุรกรรมโดยไม่ตั้งใจ

## 7. NPC Response State

หลัง NPC ประเมินข้อเสนอ ให้ UI แสดงผลในรูปแบบที่อ่านง่าย เช่น:

- Accepted — รับข้อเสนอ
- Counter Offer — เสนอราคากลับ
- Refused — ปฏิเสธ
- Suspicious — เริ่มสงสัย/ไม่ไว้ใจ
- Offended — ข้อเสนอต่ำเกินไปจนกระทบความสัมพันธ์
- Interested — สนใจข้อเสนอ แต่ต้องการรายละเอียดเพิ่ม

สถานะเหล่านี้ **สามารถเชื่อมต่อกับ NPC Memory, Reputation และ Rumor System ในภายหลัง**

## 8. Dice / Skill Check

ยังไม่บังคับให้ทุกการต่อรองต้องทอย UI สามารถรองรับผลลัพธ์ได้สองแบบ:

### Automatic Negotiation
NPC ตัดสินจากราคา สินค้า ความสัมพันธ์ และสถานการณ์

### Negotiation Check
ใช้เมื่อข้อเสนอมีความเสี่ยงหรือมีผลสำคัญ Dice/skill check จะถูกเรียกเฉพาะเมื่อระบบเห็นว่าจำเป็น

หากมีการทอย ควรแสดงเหตุผลใน UI เช่น:

> Negotiation Check  
> ข้อเสนอต่ำกว่าราคาตลาดมาก  
> Reputation  
> Relationship  
> − ความขาดแคลนสินค้า

เพื่อให้ผู้เล่นเข้าใจว่า **ทำไมถึงต้องทอย** ไม่ใช่รู้สึกว่าระบบสุ่มผลโดยไม่มีเหตุผล

## 9. Integration กับ Economy System

Negotiation UI ต้องเชื่อมกับระบบเศรษฐกิจใหม่โดยตรง:

- Currency Tiers
- Regional Prices
- Scarcity
- Regional Supply/Demand
- Direct Barter
- NPC Relationship
- NPC Memory
- Rumor Network

ดังนั้นราคาที่ NPC เสนอจะไม่ใช่ตัวเลขตายตัวเสมอไป

### หลักการ UI

- ผู้เล่นเป็นคนพูดและเสนอเอง
- ระบบเป็นคนตีความบริบท
- NPC เป็นคนตัดสินใจ
- Dice ใช้เฉพาะตอนที่ความไม่แน่นอนมีความหมาย

## 10. เป้าหมาย UX

ระบบต้องทำให้ผู้เล่นรู้สึกว่า **“ฉันกำลังต่อรองกับ NPC”** ไม่ใช่ **“ฉันกำลังเลือกค่าจาก dropdown เพื่อคำนวณราคาสินค้า”**

หน้า Play จึงควรเป็นจุดศูนย์กลางของ interaction ทั้งหมด โดยไม่บังคับให้ผู้เล่นออกจากฉากไปยังหน้า Shop แยกสำหรับการซื้อขายทุกครั้ง

## 11. สิ่งที่ยังต้องตัดสินใจก่อน implement (GAMEPLAY DECISION)

- กลไกของ Dice/skill check: อันไหนเป็น Automatic Negotiation vs Negotiation Check กำหนดอย่างไร
- ผลของสถานะ Offended/Suspicious ที่มีต่อความสัมพันธ์ ราคา และ Rumor ต้องกำหนดกฎให้ชัด
- วิธีตีความประโยค Free-text เป็น transaction (structure parsing) และความเสี่ยงของข้อเสนอที่คลุมเครือ
