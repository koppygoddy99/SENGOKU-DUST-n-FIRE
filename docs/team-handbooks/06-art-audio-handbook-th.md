## 1. พันธกิจของทีม

ทีม Art and Audio มีหน้าที่ทำให้ทุกสิ่งที่ผู้เล่นมองเห็น ได้ยิน และรับรู้ว่าเคลื่อนไหวอยู่ในเกมพูดภาษาเดียวกัน: โลกของกระดาษ บัญชีสงคราม ร่องรอยหมึก หนี้ ความทรงจำ และอำนาจที่ไม่ได้ประกาศเสียงดัง เกมไม่ใช่พิพิธภัณฑ์ญี่ปุ่น และไม่ใช่ภาพแฟนตาซีที่หยิบสัญลักษณ์ยุคเซ็นโกกุมาตกแต่งโดยไร้บริบท หน้าที่ของทีมจึงไม่ใช่ “ทำให้ดูญี่ปุ่นที่สุด” แต่คือทำให้สิ่งที่ผู้เล่นกระทำมีน้ำหนักทางกายภาพและทางสังคม

หลักการตัดสินใจของทีมมีสามข้อ ประการแรก ภาพและเสียงต้องช่วยให้ผู้เล่นอ่านความเสี่ยงได้โดยไม่แทนที่คำบรรยาย ประการที่สอง ความงามต้องไม่ลบเลือนความเหนื่อย ความสกปรก และการต่อรองที่เป็นแกนของเรื่อง ประการที่สาม ทุก asset ต้องเป็นต้นฉบับ ใช้ได้ตามสิทธิ์ หรือมีใบอนุญาตที่ตรวจสอบย้อนหลังได้

| คำมั่นทางศิลป์ | สิ่งที่ผู้เล่นควรสัมผัส | สิ่งที่ทีมต้องหลีกเลี่ยง |
|---|---|---|
| Ledger of Ash | แคมเปญของตนเหมือนสมุดบันทึกที่ผ่านมือคนจริง | dashboard สำเร็จรูปที่ไร้ตัวตน หรือ UI เกมมือถือแบบสะสมรางวัล |
| ร่องรอยมีเจ้าของ | ข้อตกลง รอยเปื้อน และตราประทับบอกว่าใครเกี่ยวข้อง | ลวดลายเพื่อความสวยงามที่ไม่มีความหมายใน state หรือเรื่อง |
| ความสงบที่ตึงอยู่ | ผู้เล่นมีพื้นที่อ่าน คิด และตัดสินใจ | เอฟเฟกต์ดัง กระพริบ หรือภาพรุนแรงที่แย่งความสนใจจาก prose |
| ขอบเขตประวัติศาสตร์ | โลกมีบรรยากาศจริงโดยไม่สวมรอยของจริง | การอ้างตรา ตระกูล บุคคล หรือเอกสารจริงโดยไร้หลักฐานและสิทธิ์ |

## 3. ภาษาเชิงภาพ Ledger of Ash

### 3.1 ภาพรวมของระบบ

ภาพหลักของเกมคือแผ่นกระดาษ off-white ที่ถูกใช้งาน ไม่ใช่กระดาษเก่าคร่ำครึจนอ่านข้อความยาก หมึก navy ทำหน้าที่เป็นภาษาเนื้อหาและโครงสร้าง Vermilion มีไว้สำหรับการกระทำ คำเตือน หรือรอยที่ไม่ควรถูกมองข้าม Ochre ใช้กับทรัพยากร เวลา และสิ่งที่อยู่ระหว่างการตัดสินใจ Teal ใช้เป็นสัญญาณของการยืนยัน การเชื่อมโยง หรือเส้นทางที่เปิดอยู่ สีทั้งหมดต้องทำงานเป็นลำดับชั้น ไม่ใช่ถูกใช้เพื่อย้อมแต่ละกล่องให้ต่างกัน

พื้นผิวเป็น “เสียงเบา” ของหน้า ไม่ใช่รูปภาพพื้นหลังที่อ่านได้ชัด ห้ามใช้ texture ที่ลด contrast หรือสร้างความรู้สึกว่าข้อความเป็นของเก่าอ่านไม่ออก พื้นที่ว่างคือสิ่งที่ปกป้องจังหวะการอ่าน prose และต้องถือเป็นทรัพยากรการออกแบบเช่นเดียวกับสี

| Token | ค่าอ้างอิง | ความหมาย | การใช้ที่อนุญาต |
|---|---:|---|---|
| Paper | `#fbfaf6` | แผ่นบันทึกที่ยังมีชีวิต | พื้นหลักและพื้นที่อ่านยาว |
| Ink Navy | `#102b49` | หมึก หลักฐาน โครงสร้าง | ข้อความหลัก เส้นนำสายตา และ metadata สำคัญ |
| Dust Vermilion | `#b52b2f` | การตัดสินใจ รอยเลือดเชิงนามธรรม คำเตือน | CTA หลัก ผลเสี่ยง และ state ที่ต้องตอบสนอง |
| Oath Ochre | `#b9861f` | เวลา เสบียง ภาระที่ยังค้าง | badge รอง ความคืบหน้า และ resource cue |
| River Teal | `#176c61` | ทางผ่าน การยืนยัน การเชื่อมต่อ | success context, map path และ state ที่เชื่อมโยง |

ค่าอ้างอิงนี้ต้องถูกประกาศเป็น design token ใน CSS หรือระบบ token เดียว ไม่ hard-code เฉดสีใหม่ใน component เพื่อแก้ปัญหาเฉพาะหน้า หากต้องเพิ่มสี ต้องระบุ semantic role, contrast, สถานะ dark mode (ถ้ามี) และเหตุผลที่ token เดิมทำไม่ได้

### 3.2 วัตถุภาพและ artifact language

วัตถุภาพหลัก ได้แก่ ขอบกระดาษ รอยหมึก เส้นบัญชี รอยพับ แถบตรารับรอง พิกัดแผนที่อย่างหยาบ เชือก ผืนผ้า รอยรองเท้า และสัญลักษณ์ของเสบียง สิ่งเหล่านี้ใช้เพื่อบอกชนิดของข้อมูล เช่น agreement เป็นบันทึกที่มีคู่กรณีและพยาน, Chronicle เป็นใบเรื่องที่กลับไปอ่านได้, Map เป็นพื้นที่ที่ข่าวและการเดินทางตัดกัน มิใช่คลัง prop ที่ใส่ทุกอย่างพร้อมกัน

อย่าใช้ตราตระกูลจริง โลโก้ของหน่วยทหารจริง ภาพตราประทับที่ทำให้ดูเหมือนเอกสารราชการแท้ หรือ mon ที่คัดลอกมาจากแหล่งสาธารณะโดยไม่มีสิทธิ์ แม้รูปแบบทางเรขาคณิตจะไม่ซับซ้อน การคัดลอกเชิงภาพยังทำให้เกมเสี่ยงต่อความเข้าใจผิดและการอ้างตนเกินจริง ให้ใช้เครื่องหมายสมมติที่เป็น original campaign fiction และกำกับใน lore ว่าเป็นบ้าน ชุมชน หรือเครือข่ายสมมติ

| ชนิดของข้อมูล | ภาษาวัตถุภาพที่เหมาะ | ข้อห้าม |
|---|---|---|
| Intent และผลทอย | เส้นหมึก ลำดับตัวเลขที่อ่านง่าย รอยกดเล็กน้อย | ลูกเต๋า 3D ใหญ่จนกลบผลหรือ prose |
| Chronicle / Leaf | folio, margin note, tab ของวันและฤดู | กระดาษฉีกเละหรือฟิลเตอร์ aged ที่อ่านข้อความลำบาก |
| Agreements & Consequences | บรรทัดคู่สัญญา ช่องพยาน ขอบตราสมมติ | เครื่องหมายขององค์กรหรือแคว้นจริงโดยไร้ source |
| Mission Dossier | กระดาษพับประกาศงานและเส้น deadline | checklist เกมแนว productivity ที่ให้กดรับ/ส่ง |
| Map | เส้นทาง แหล่งน้ำ เนินขอบเขต และหมุดเรื่อง | แผนที่ประเทศจริงที่สื่อว่าแคมเปญครอบคลุมพื้นที่จริงทั้งหมด |

## 4. Typography และภาษาใน UI

### 4.1 หน้าที่ของตัวอักษร

เกมมี UI ภาษาอังกฤษเป็นหลักและไทยเป็นภาษารองที่สลับได้ ฟอนต์จึงต้องอ่านได้ต่อเนื่องและมี glyph ครบทั้งสองระบบอักษร Noto Serif Thai ใช้กับ prose, Chronicle และหัวข้อที่ต้องให้ฟีลการอ่าน; Noto Sans Thai ใช้กับ metadata, control และข้อความที่ต้องสแกนเร็ว; Poppins ใช้กับตัวเลข สถานะ และ UI ภาษาอังกฤษในขนาดที่ต้องคงรูปทรง การใช้ฟอนต์เกินสามตระกูลต้องผ่าน art review เพราะจะทำให้ต้นทุนโหลดและบุคลิกหน้าจอแตก

โครงสร้างตัวอักษรต้องแยก “สิ่งที่เกิดขึ้น” ออกจาก “สิ่งที่ระบบบอก” อย่างชัดเจน Prose มี leading กว้างกว่าข้อความ UI, ผลทอยต้องอ่านตัวเลขและ margin ได้ในทันที, และ text ที่เป็น Historical Fence หรือ Local Trial ต้องตรงไปตรงมา ไม่แต่งด้วยภาษากวีเพื่อซ่อนข้อจำกัดของระบบ

| ระดับ | การใช้ | หลักการ | ห้ามใช้ |
|---|---|---|---|
| Display | ชื่อแคมเปญ ชื่อ Leaf หัวข้อหลัก | ไม่เกินสองบรรทัดใน viewport สำคัญ | ฟอนต์ display ที่ไม่มีอักษรไทยครบหรืออ่านยาก |
| Prose | ฉาก เกมลอค และ Reader Mode | ความกว้างบรรทัดพอดี พื้นที่หายใจชัด | ตัวอักษรเล็กเพื่อยัดเรื่องมากขึ้น |
| Ledger | stat, agreement, mission, metadata | ตัวเลขจัดแนวและมี label เสมอ | icon ล้วนโดยไม่มี accessible name |
| System notice | AI fallback, save status, error | อธิบายเหตุและทางไปต่อ | สีอย่างเดียวโดยไม่มีข้อความ |

### 4.2 ภาษาและความละเอียดอ่อนเชิงวัฒนธรรม

Art and Audio ต้องไม่ทำให้ภาษาในฉากกลายเป็นพร็อพ หากมีอักษรญี่ปุ่นในภาพ ต้องเป็นข้อความที่ตรวจความหมายได้ มีเหตุผลในโลก และผ่าน Game Director; ห้ามใช้ตัวอักษรสุ่มเพื่อสร้าง “บรรยากาศเอเชีย” ห้ามใช้ calligraphy ที่คัดลอกจากเอกสารศักดิ์สิทธิ์ บทกวี หรือสัญลักษณ์จริงโดยไม่ตรวจสิทธิ์และบริบท

สำหรับ UI คำอังกฤษต้องเป็น primary label ที่สั้น กระชับ และ consistent ส่วนไทยต้องเป็นคำรองที่ให้ความหมาย ไม่ใช่คำแปลประดับ คำที่มองเห็นพร้อมกันต้องไม่ขัดกัน เช่น `Declare Intent / ประกาศเจตนา`, `Current Leaf / ใบเรื่องปัจจุบัน`, `Local Trial / โหมดเล่นต่อในเครื่อง` ทุกการตัดสินใจด้านคำต้องอ้างอิง language register ใน Lore Bible

## 5. Motion: การเคลื่อนไหวที่มีน้ำหนักแต่ไม่รบกวน

### 5.1 หลักการ

Motion ใน Dust & Fire มีหน้าที่บอกว่าข้อมูลใดเพิ่งเปลี่ยนและผู้เล่นควรมองไปที่ใด ไม่ใช่การทำให้ทุกการกดดูน่าตื่นเต้น การทอย 2d12 เป็นเหตุการณ์สำคัญเพียงไม่กี่ครั้งที่ใช้ motion เด่นได้ แต่หลังจากผลปรากฏ เนื้อหาใหม่ต้องเข้าสู่พื้นที่อ่านอย่างสงบ ช่วงเวลาระหว่าง “กด” กับ “รู้ผล” ต้องไม่ใช้เพื่อลวงว่ามีการสุ่มที่ไม่ได้เกิดขึ้นจริง

ใช้เฉพาะ `transform` และ `opacity` เป็นหลัก ระยะสั้นสำหรับ control และยาวขึ้นเฉพาะ transition ระหว่างฉากหรือการเปิด Leaf การเคลื่อนไหวต้องทำงานได้แม้ JavaScript ช้าและต้องปิดหรือย่อลงเมื่อระบบรายงาน `prefers-reduced-motion`.

| เหตุการณ์ | ภาพเคลื่อนไหวที่แนะนำ | ระยะอ้างอิง | เหตุผล |
|---|---|---:|---|
| กด CTA | scale ลงเล็กน้อยและคืนกลับ | 100–160 ms | ยืนยันว่าระบบรับคำสั่ง |
| เปิด drawer หรือ rail | translate + opacity จากจุดควบคุม | 180–260 ms | รักษาทิศทางใน shell |
| ทอย 2d12 | การเคลื่อนที่สั้นของลูกเต๋าและการหยุดอ่านค่า | ไม่เกิน 900 ms รวม | สร้างจังหวะแต่ไม่ถ่วงการเล่น |
| ผลลัพธ์และ ledger update | opacity + translate เล็กน้อยแบบเรียงลำดับ | 180–280 ms | แยกผล กติกา และ prose |
| เปิด Leaf ใหม่ | transition ของ folio ที่ไม่บังเนื้อหา | ไม่เกิน 350 ms | บอกการเปลี่ยนหน่วยเรื่อง |

### 5.2 Reduced motion และการเข้าถึง

เมื่อ `prefers-reduced-motion: reduce` ระบบต้องแสดงผลทอยและ consequence ทันทีหรือด้วย fade ที่สั้นมาก ไม่มีการสั่น หมุน ลูกเต๋าพุ่ง หรือ parallax Motion ต้องไม่เป็นเงื่อนไขในการเข้าใจว่า roll จบแล้ว; ต้องมีข้อความสถานะและ focus management ที่สื่อผลแบบเดียวกัน

ห้ามใช้ flash เพื่อแทน critical hit, failure, เลือด หรือความตกใจ ห้าม autoplay animation ที่ไม่หยุด และห้ามให้ motion เป็นเพียงสัญญาณเดียวของสถานะใด ๆ ทุก cue เชิงภาพต้องมี label, color ที่มี contrast และ semantic text ร่วมเสมอ

## 6. Sound direction

### 6.1 บุคลิกเสียง

เสียงของเกมเป็นองค์ประกอบรองที่ยืนยันสัมผัสของโลก ไม่ใช่ soundtrack ที่ไหลกลบการอ่าน เสียงหลักควรใกล้ตัวและมีวัสดุ เช่น กระดาษ, ไม้, เชือก, ผ้า, เท้าเดินบนพื้น, ลมไกล ๆ, ประตูหรือชามที่กระทบเบา ๆ หลีกเลี่ยงการใช้ชุดเสียงตะวันออกแบบเหมารวม เช่น เครื่องดนตรีหรือเสียงร้องที่ถูกตัดออกจากบริบทเพื่อบอกผู้เล่นว่า “นี่คือญี่ปุ่น”

ดนตรีเชิงธีมใช้เฉพาะจุดเปลี่ยนสำคัญ เช่น เปิดแคมเปญ, Leaf ใหม่, การคลี่คลาย mission หรือ Reader Mode ไม่ควรมี loop ต่อเนื่องเป็นค่าเริ่มต้น เพราะเกมมี prose มากและผู้เล่นอาจต้องการอ่านเงียบ ๆ ให้ ambient, music, UI และ narration เป็น bus ที่ปรับได้แยกกันใน Settings เมื่อ feature พร้อม

| ชั้นเสียง | วัตถุประสงค์ | ตัวอย่าง cue | ข้อจำกัด |
|---|---|---|---|
| UI micro | ยืนยันการกระทำ | กด CTA, บันทึกสำเร็จ, เปิดเมนู | สั้น เบา ไม่ซ้ำถี่จนเหนื่อย |
| Dice / outcome | ทำให้ผลมีน้ำหนัก | ลูกเต๋าหยุด, margin ปรากฏ, Momentum ใช้ | ต้องไม่ตีความ outcome ด้วยเสียงอย่างเดียว |
| World ambience | สร้างพื้นที่รอบ prose | ลม ตลาดห่าง ๆ ฝน เสียงเรือ | เลเยอร์ต่ำ ปิดได้ และไม่ loop เห็นรอยตัดง่าย |
| Narrative transition | ทำเครื่องหมายเรื่อง | เปิด Leaf, mission resolve, Reader Mode | ใช้น้อย มีความหมาย ไม่ทำทุกครั้ง |
| Accessibility | ช่วยนำทางโดยสมัครใจ | focus cue, screen-reader-adjacent confirmation | ต้องไม่แทน ARIA/live text |

### 6.2 Audio event map

ทุกเสียงต้องมีชื่อ event, trigger, priority, cooldown, ทางเลือกเมื่อปิดเสียง และเจ้าของ state ที่อ้างอิงได้ เอกสาร event map อยู่ใน repository และ review ร่วมกับ Game Development ไม่ให้ component เรียกไฟล์เสียงกระจัดกระจายโดยไม่มีข้อจำกัดความถี่ ตัวอย่างเช่น `roll.resolved` เกิดได้หนึ่งครั้งต่อ roll id; `save.completed` ต้องไม่เล่นซ้ำจาก rerender; `local_trial.announced` เป็นข้อความสำคัญจึงต้องมีทางผ่านเป็น text ก่อนเสียง

| Event key | Trigger เชิงระบบ | การตอบสนองเสียง | Cooldown/เงื่อนไข |
|---|---|---|---|
| `intent.confirmed` | ผู้เล่นยืนยัน intent | หมึกแตะกระดาษเบามาก | ไม่เกินหนึ่งครั้งต่อ intent id |
| `roll.revealed` | deterministic total พร้อมแสดง | ลูกเต๋า/ไม้หยุด | ต้องเคารพ reduced motion และ mute |
| `momentum.used` | state ลด Momentum สำเร็จ | กดตราหรือเชือกรัดสั้น | ไม่เล่นเมื่อ mutation ล้มเหลว |
| `leaf.opened` | วันสะสมถึงเงื่อนไข | ลม/กระดาษพลิกสั้น | หนึ่งครั้งต่อ Leaf id |
| `save.completed` | Local Save เขียนสำเร็จ | ยืนยัน UI เบามากหรือเงียบ | ไม่เล่นจาก auto save ถี่ ๆ โดยค่าเริ่มต้น |
| `local_trial.fallback` | AI provider ใช้ไม่ได้ | ไม่มีเสียงบังคับ; ให้ notice ชัด | ต้องไม่สื่อว่าเป็นความล้มเหลวของผู้เล่น |

### 6.3 ระดับเสียงและข้อควรคำนึง

Master output ต้องไม่ทำให้ UI cue ดังเกิน prose narration หรือ audio อื่น หลีกเลี่ยง peak ที่ทำให้ผู้เล่นตกใจโดยเฉพาะหลังการทอยล้มเหลว เสียงที่สื่อ violence ต้องมีเหตุผลและอยู่ในระดับสอดคล้องกับ narrative content policy ไม่ใช้เสียงกรีดร้องหรือภาพเสียงรุนแรงเพื่อเร่งอารมณ์ โดยเฉพาะในฉากที่ผู้เล่นไม่ได้เลือกเผชิญความรุนแรงตรง ๆ

เมื่อมี TTS หรือ narration ในอนาคต เสียงบรรยายต้องเป็น feature ที่ผู้เล่นเริ่มเอง ไม่ auto-play, ต้องมี transcript, pause, restart และ slider แยกจาก music/ambient ห้ามใช้เสียงเลียนบุคคลจริง นักแสดง หรือบุคคลประวัติศาสตร์โดยไม่ได้รับสิทธิ์ชัดเจน

## 7. นโยบาย asset และสิทธิ์

### 7.1 หลัก original-first

ทุก asset เข้าเกมได้เมื่ออยู่ในหนึ่งในสี่สถานะ: (1) ผลิตต้นฉบับโดยทีมและมีการโอนสิทธิ์ตามสัญญา, (2) สร้างด้วยเครื่องมือที่สิทธิ์การใช้งานอนุญาตและมีบันทึก prompt/reference ที่ไม่ละเมิด, (3) ใช้ stock หรือ font ภายใต้ licence ที่ครอบคลุมเว็บและการเผยแพร่, หรือ (4) public-domain/CC asset ที่ตรวจเงื่อนไข attribution และ adaptation แล้ว คำว่า “หาเจอในอินเทอร์เน็ต” ไม่ใช่สถานะสิทธิ์

ห้าม trace ภาพ, sample เสียง, คัดลอก sprite, rip asset จากเกม หนัง ซีรีส์ หรือมังงะ แม้ใช้เพื่อ placeholder หากต้องใช้ placeholder ให้ใช้ shape, tone และเสียงชั่วคราวที่ทีมสร้างเองหรือ asset library ที่อนุญาตเท่านั้น Placeholder ทุกชิ้นต้องติดป้าย `TEMP` ใน asset register และมีวันหมดอายุ/owner

| ฟิลด์ asset register | เหตุผล |
|---|---|
| Asset ID และชื่ออ่านง่าย | เชื่อมกับโค้ดและการ review |
| ชนิด/รูปแบบ/ขนาด | คุม performance และความเหมาะสม |
| เจ้าของงานและวันที่สร้าง | ระบุผู้รับผิดชอบการแก้ |
| ที่มาและสถานะสิทธิ์ | ตรวจลิขสิทธิ์ย้อนหลัง |
| Licence URL/ไฟล์หลักฐาน | ใช้เมื่อ release audit |
| Historical classification | แยก original fiction ออกจาก fact-supported reference |
| หน้า/feature ที่ใช้ | ประเมินผลกระทบเมื่อเปลี่ยนหรือนำออก |
| Accessibility note | alt, transcript, caption หรือ reduced-motion behavior |

### 7.2 ภาพจาก AI และ reference

หากใช้เครื่องมือสร้างภาพ/เสียงด้วย AI ทีมต้องใช้เฉพาะบริการและ terms ที่โครงการอนุมัติ บันทึก prompt, model/service, วันที่สร้าง, reference ที่ป้อน และการ retouch ที่ทำ ไม่ป้อนภาพลิขสิทธิ์ของบุคคลที่สามเพื่อเลียนแบบ style, ไม่สั่งให้สร้างงาน “ในสไตล์” ศิลปินมีชีวิต และไม่ปล่อยงานที่มี watermark, text ผิด, hands/weapon ที่ชวนเข้าใจผิด หรือสัญลักษณ์ทางประวัติศาสตร์ที่ไม่ผ่าน review

AI-generated asset เป็น draft ที่ต้องผ่าน human art direction, rights check และ visual quality check เหมือน asset อื่น ไม่มีข้อยกเว้นเพราะสร้างเร็ว หาก asset ใดทำให้ผู้เล่นเชื่อว่าเป็นสถานที่ บุคคล ตระกูล หรือเอกสารจริง ต้องผ่าน Game Director และมี language/fact boundary ในบริบทที่เหมาะสม

## 8. กระบวนการผลิตและการส่งมอบ

### 8.1 จาก brief สู่ asset

ทุกงานเริ่มจาก brief หนึ่งหน้าอย่างน้อย: goal ของผู้เล่น, page/feature, state ที่ต้องมองเห็น, classification ทางประวัติศาสตร์, ข้อความ/ภาษา, viewport สำคัญ, accessibility และ performance budget ทีมต้องนำเสนอ direction ต่ำความละเอียดก่อนผลิต final เพื่อลดการแก้ asset ที่สวยแต่ไม่ตอบโจทย์ระบบ

ขั้นต่อไปคือ review ข้ามทีม หากงานเชื่อม UI ต้องมี component contract; หากงานสื่อผล state ต้องมี event/state reference; หากเป็นภาพเรื่องต้องมี narrative use case; หากเป็นเสียงต้องมี event key เมื่อผ่านแล้วจึงทำ production, export ตามมาตรฐาน, ลงทะเบียน asset, integration, visual/audio QA และ sign-off

```text
Brief → historical/rights check → low-fidelity direction
→ cross-team review → production → asset register
→ integration contract → accessibility/performance QA → sign-off
```

### 8.2 Naming และ export

ใช้ชื่อไฟล์ lowercase, kebab-case, มี feature และสถานะ เช่น `play-roll-reveal-v01.ogg`, `chronicle-leaf-divider-v02.svg` ไม่ใช้ชื่อคลุมเครืออย่าง `final-final2.png` ให้ source file, export, licence note และ preview อยู่ในตำแหน่งที่ทีมกำหนด โดยไม่มี binary ขนาดใหญ่ฝังใน project web หากเป็น asset ของเว็บ ให้จัดเก็บตามนโยบาย asset hosting ของโครงการและใช้ URL ที่ได้รับจากกระบวนการ upload เท่านั้น

สำหรับ icon ให้ใช้ vector ที่เป็น original หรือ icon library ที่ licence ครอบคลุมและมี mapping ชัดเจน icon ต้องมี text label หรือ tooltip/aria label เมื่อแสดงลำพัง ห้ามใช้ icon ที่ตีความได้หลายอย่างเพื่อแทนคำสั่งสำคัญ เช่น Save, Load, Delete หรือ Local Trial

## 9. Performance และการเข้าถึง

ภาพไม่ควรถูกใช้เป็นฉากหลังขนาดใหญ่หาก CSS shape, token หรือ typography ให้ความหมายเดียวกันได้ ทุกภาพต้องมีขนาดพอดีกับการใช้งาน, format ที่เหมาะ, dimension ระบุล่วงหน้าเพื่อลด layout shift และ lazy-load เมื่ออยู่นอกพื้นที่สำคัญ ยกเว้น asset ที่เป็น LCP element ซึ่งต้องถูกจัดการตาม performance plan

เสียงไม่โหลดไฟล์ใหญ่หรือเริ่ม decode ทั้ง library ตั้งแต่เปิดหน้า ให้โหลดตาม interaction/scene และมี fallback เงียบที่ไม่พัง flow ถ้า audio policy ของเบราว์เซอร์ปฏิเสธ autoplay ทีมต้องถือว่านี่เป็น behavior ปกติ ไม่ทำ modal ขัดผู้เล่นเพื่อบังคับเปิดเสียง

| หัวข้อ | เกณฑ์ขั้นต่ำก่อนส่ง QA |
|---|---|
| Contrast | ข้อความ, control และ status ผ่านเกณฑ์ที่ UI/UX/QA กำหนดในทุก state สำคัญ |
| Alt / transcript | ภาพที่มีข้อมูลมี alt ที่สื่อความหมาย; เสียงสำคัญมีข้อความทดแทน |
| Keyboard | ไม่มี action สำคัญที่ต้องใช้ drag หรือ pointer-only |
| Reduced motion | dice, Leaf, drawer และ transition ทุกชนิดมี behavior ลดการเคลื่อนไหว |
| Mobile | งานภาพไม่ทำให้หน้า overflow และ tap target ไม่เล็กเกินเกณฑ์ทีม UI/UX |
| Network | asset ไม่ทำให้หน้าเล่นรอภาพ/เสียงก่อนเปิด intent composer |

## 10. เกณฑ์ตรวจรับและ checklist

งาน visual/audio จะถือว่าเสร็จเมื่อมีคุณภาพด้านความหมาย สิทธิ์ การใช้งาน และการส่งมอบ ไม่ใช่เพียงผ่านการอนุมัติทางรสนิยม งานที่ทำให้ UI อ่านยาก, กลบ prose, ไม่รู้ที่มา หรือไม่ทำงานเมื่อปิด motion/audio ยังไม่เสร็จ

### Checklist ก่อนส่งต่อ

- [ ] Asset สนับสนุน state หรือ narrative ที่ระบุใน brief ได้จริง และไม่เป็นของตกแต่งลอย ๆ
- [ ] ใช้ palette/token ที่อนุมัติ ไม่มีสีหรือฟอนต์เฉพาะกิจที่ทำให้ระบบแตก
- [ ] ไม่มีตรา ชื่อ ภาพ เอกสาร หรือสัญลักษณ์จริงที่อาจทำให้เข้าใจว่าเกมยืนยันข้อเท็จจริงโดยไม่มี source
- [ ] สิทธิ์/ที่มา/owner ถูกบันทึกครบใน asset register
- [ ] UI text, alt, transcript และ labels ไม่ใช้สีหรือเสียงเป็นช่องทางเดียว
- [ ] Reduced motion, mute และ autoplay restriction มีทางผ่านที่ใช้งานได้
- [ ] ทดสอบ desktop และ mobile กับ component จริง ไม่ตรวจเฉพาะ artboard
- [ ] ผ่าน review ของ UI/UX, Game Director และ QA ตามประเภทงาน

## 11. Definition of Done ของทีม Art and Audio

งานหนึ่งชิ้นเสร็จเมื่อผู้เล่นอ่านการกระทำของตนได้ชัดขึ้น ไม่ใช่เมื่อหน้าเต็มขึ้น; เมื่อ asset มีสิทธิ์ใช้จริง ไม่ใช่เมื่อหาแหล่งที่หน้าตาคล้ายกัน; และเมื่อการปิดเสียงหรือการลด motion ไม่ทำให้ผู้เล่นสูญเสียข้อมูลเกม ทีมต้องพร้อมอธิบายได้ว่าองค์ประกอบนั้นมีหน้าที่อะไร อยู่ใน state ใด มีที่มาใด และจะเปลี่ยนอย่างไรหาก story, UI หรือ release constraint เปลี่ยน
