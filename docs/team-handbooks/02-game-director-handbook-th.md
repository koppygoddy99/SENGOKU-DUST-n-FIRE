# คู่มือทีม 1: Game Director — Dust & Fire: Sengoku Stories

## 1. อำนาจหน้าที่และผลลัพธ์ที่ทีมต้องรับผิดชอบ

Game Director เป็นเจ้าของ **ความหมายของเกม** ไม่ใช่เจ้าของทุก feature หน้าที่ของทีมคือทำให้ทุกการตัดสินใจตอบคำถามเดียวกันว่า “สิ่งนี้ทำให้ผู้เล่นรู้สึกว่ากำลังมีชีวิตอยู่ในโลกที่เกียรติ อำนาจ หนี้ ความรัก และความกลัวมีราคาจริงหรือไม่” ทีมกำหนดวิสัยทัศน์ กลุ่มผู้เล่น ขอบเขต MVP ลำดับความสำคัญของงาน น้ำเสียงทางวัฒนธรรม และเกณฑ์ที่ต้องอนุมัติก่อนเปลี่ยนกติกาหรือเนื้อหาสำคัญ

ผลลัพธ์ขั้นต่ำของทีมประกอบด้วย product vision ที่สื่อสารได้ในหนึ่งหน้า, decision log ที่บอกเหตุผลของข้อเลือกสำคัญ, content policy สำหรับประวัติศาสตร์และความรุนแรง, scope map ที่แยก MVP ออกจาก roadmap, และ approval record สำหรับการเปลี่ยน feature ที่กระทบเจตนาของเกม ผู้กำกับเกมไม่ควรเขียนโค้ดแทน Game Development หรือออกแบบทุก wireframe แทน UI/UX แต่ต้องทำให้ทีมเหล่านั้นรู้ว่าอะไรคือ “สิ่งที่ห้ามเสีย” เมื่อมี trade-off

## 2. Product Thesis

Dust & Fire ไม่ใช่เกมที่ถามว่า “ผู้เล่นฆ่าศัตรูได้กี่คน” แต่ถามว่า “เมื่อผู้เล่นใช้ชื่อ เอกสาร ความสามารถ หรือความรุนแรงเพื่อผ่านเรื่องหนึ่ง ใครบ้างที่ต้องจำและใครต้องเป็นคนจ่าย” เกมนำเสนอสงครามผ่านรอยร้าวในชีวิตประจำวัน: ตลาดที่ข้าวแพงขึ้น, ประตูด่านที่เปลี่ยนเวร, ใบผ่านที่กลายเป็นหนี้, คนส่งสารที่ไม่กล้าพูดชื่อเจ้านาย, และคนในชุมชนที่ต้องเลือกว่าจะช่วยใครก่อน

ผู้เล่นมี agency เพราะเขาเลือกเจตนา วิธี และคนที่ยอมทิ้งไว้ข้างหลัง ระบบมี authority เพราะมันบันทึกผลและไม่ยอมให้ความเก่งลบโลก ผู้เล่นจึงสามารถเติบโตเป็นคนมีชื่อเสียง ผู้มีอิทธิพล คนของบ้านใหญ่ หรือผู้รอดชีวิตที่ไม่มีใครจำชื่อได้ โดยเกมไม่บังคับเส้นชัยทางศีลธรรมหนึ่งแบบ

| เสาหลัก | คำอธิบาย | ตัวอย่างที่ถูกต้อง | สัญญาณว่าออกนอกทิศ |
|---|---|---|---|
| ราคาของการเลือก | การสำเร็จต้องทิ้งรอย | ได้ใบผ่าน แต่ถูกจดชื่อโดยด่าน | ชนะแล้วทุก NPC รักผู้เล่นทันที |
| สถานะเป็นแรงกดดัน | ฐานะเปิด/ปิดทาง ไม่บังคับคน | พ่อค้าให้เครดิตแต่ขอพยาน | ค่า Honor สูงแล้วสั่ง NPC ได้ |
| โลกมีชีวิต | เวลา ข่าว ข้อตกลง และชุมชนตอบสนอง | สี่วันผ่านไป ข่าวถึงตลาดใหม่ | ทุก scene เกิดในสุญญากาศ |
| ประวัติศาสตร์เป็นรั้ว | ความจริงช่วยคุมความน่าเชื่อ | บอกว่าเป็น contextual-play เมื่อฉากสมมติ | อ้างชื่อหรือเหตุการณ์จริงโดยไม่มีหลักฐาน |
| นิยายก่อนระบบ | ผู้เล่นเห็นคนและผลก่อนศัพท์เทคนิค | ร้อยแก้วตามหลังผลทอยในฉากเดิม | หน้าจอเต็มไปด้วย modifier ก่อนเรื่อง |

## 3. กลุ่มผู้เล่นและความต้องการที่ต้องปกป้อง

กลุ่มหลักคือผู้เล่นที่ชอบนิยายโต้ตอบ การเมือง ความสัมพันธ์ และ tabletop ที่มีผลตามรอยได้ กลุ่มนี้ไม่ต้องการอ่าน rulebook ก่อนเล่นนาน แต่ต้องการเชื่อว่าระบบไม่โกงและโลกไม่ลืม กลุ่มรองคือผู้เล่นที่สนใจเซ็นโกกุในฐานะบริบททางสังคมและอยากเริ่มจากอาชีพทั่วไป ไม่จำเป็นต้องเป็นซามูไรหรือผู้นำทัพ

ผู้เล่นใหม่ต้องเปิดเกมแล้วเห็นว่า “ข้าพูดหนึ่งประโยคได้” ผู้เล่นกลางทางต้องเห็นว่า “ฉันเก่งอะไรขึ้น และเวลาเปลี่ยนอะไร” ผู้เล่นระยะยาวต้องเห็นว่า “โลกผูกฉันเข้ากับชื่อ คน และสัญญาอย่างไร” หาก feature ใดไม่ช่วยคำถามหนึ่งในสามนี้ ให้เลื่อนออกจาก MVP ก่อน

## 4. แนวเนื้อเรื่องและการรีเซ็ต Narrative Direction

### 4.1 ขอบเขตการเล่าเรื่อง

เรื่องหลักควรสร้างจากความตึงเครียดสามขนาดพร้อมกัน ขนาดเล็กคือการอยู่รอดของร่างกายและคนใกล้ตัว ขนาดกลางคือชุมชน เครือข่ายค้า บ้าน หรือกลุ่มติดอาวุธ ขนาดใหญ่คือการเปลี่ยนฝ่าย อำนาจท้องถิ่น เส้นทาง และแรงสะเทือนของสงคราม ผู้เล่นไม่ต้องถูกโยนเข้าหา “ชะตากรรมกอบกู้แผ่นดิน” ตั้งแต่ต้น แต่การเลือกเล็ก ๆ ต้องสามารถกลายเป็นเหตุให้คนใหญ่โตเริ่มจำชื่อได้

การรีเซ็ต narrative direction ของ Dust & Fire ให้ตั้งต้นที่คำถามนี้: **ใครเป็นคนต้องรับผิดชอบเมื่อคนมีอำนาจบอกว่าไม่มีใครรับผิดชอบ** ภารกิจไม่ควรเป็น “ไปฆ่าเป้าหมาย” ลอย ๆ แต่ควรเป็นการส่งคนข้ามด่าน, ตัดสินข้าวและแรงงาน, ปกป้องหรือปลอมแปลงเอกสาร, ซ่อมอาวุธภายใต้แรงกดดัน, ต่อรองสิทธิ์ทางน้ำ, หรือเลือกว่าจะเอาความจริงไปขายให้ใคร

### 4.2 Narrative Arc Framework

โครงเรื่องเป็นกรอบสำหรับสร้าง campaign ไม่ใช่เนื้อหาบังคับ ผู้เล่นอาจอยู่ใน arc เดียวหลาย Leaf หรือข้าม arc ตามผลของโลก

| Arc | คำถามหลัก | สิ่งที่เปลี่ยนใน state | จุดจบที่ยอมรับได้ |
|---|---|---|---|
| 1. แรงกดดันแรก | ใครกำลังบังคับให้ผู้เล่นเลือก | mission offered/active, first memory, first agreement | ซื้อเวลา, ยอมจำนน, หรือสร้างศัตรูคนแรก |
| 2. ชื่อที่เริ่มเดิน | ผู้คนเรียกผู้เล่นว่าอะไรและเพราะอะไร | mastery Step, honor/stain, witness | ได้ชื่อเสียง, ถูกป้ายสี, หรือถูกผูกกับบ้านหนึ่ง |
| 3. ขอบเขตของบ้าน | ผู้เล่นยอมเสียอะไรให้ชุมชนหรือเครือญาติ | resource, oath, debt, community memory | บ้านรอด, บ้านแตก, หรือผู้เล่นกลายเป็นคนนอก |
| 4. อำนาจที่ยืมมา | ผู้เล่นใช้ตรา ใบผ่าน หรือกองกำลังของใคร | influence, access, agreements | มีสิทธิ์มากขึ้นพร้อมหนี้ที่หนักขึ้น |
| 5. ราคาของตำนาน | เมื่อชื่อของผู้เล่นมีน้ำหนัก โลกตอบแทนหรือไล่ล่าอย่างไร | Mastery Mark, rivals, legacy memories | ขึ้นสูง, ลี้ภัย, สูญเสียคนสำคัญ, หรือเลือกไม่เป็นตำนาน |

โครง arc ขนาดใหญ่ เช่น ผู้เล่นสร้างอำนาจจนเป็น “โชกุนเปื้อนเลือด” หรือทิ้งทุกอย่างแล้วตายอย่างโดดเดี่ยวในป่า เป็น **ปลายทางเชิงธีม** ที่ต้องเกิดจากหลาย campaign state ไม่ใช่ scripted ending และไม่ควรอยู่ใน MVP จนกว่าระบบความสัมพันธ์ บ้าน และเวลาหลายปีรองรับได้จริง

### 4.3 กฎของฉาก

ฉากหนึ่งต้องมีสถานที่ที่สัมผัสได้, แรงกดดันที่คนในฉากเข้าใจ, ผู้มีเสียงพูดหรือมีอิทธิพล, สิ่งที่ผู้เล่นเสี่ยงจะเสีย, และการเปิดให้ผู้เล่นตั้งเจตนาได้หลายแบบ ฉากที่ดีไม่เฉลยคำตอบด้วย suggested actions ทั้งหมด และไม่ลงโทษผู้เล่นเพราะเลือกวิธีนอกเมนู

ทุก resolution จาก AI GM ต้องมีอย่างน้อยสามย่อหน้า ย่อหน้าแรกแสดงผลที่เกิดขึ้นกับสิ่งที่ผู้เล่นทำ ย่อหน้าที่สองแสดงปฏิกิริยา NPC และแรงกดดันสังคม ย่อหน้าที่สามเปิดสิ่งที่เปลี่ยนและคำถามถัดไป ร้อยแก้วต้องมีรายละเอียดรูปธรรมอย่างน้อยหนึ่งอย่างต่อย่อหน้า เช่น ผิวไม้เปียก, กลิ่นเขม่า, รอยเชือก, เสียงด่าน, ขอบเอกสาร, หรือท่าทางคนที่ไม่กล้าสบตา

## 5. Historical and Content Governance

Game Director เป็นผู้บังคับใช้ Historical Fence ร่วมกับ Game Design และผู้ดูแล content ห้ามใช้คำว่า “ตามประวัติศาสตร์จริง” กับ NPC สมมติหรือเหตุการณ์ที่ไม่ได้มี source ตรง ความสมจริงเชิงโครงสร้าง เช่น การมีช่างโลหะ เส้นทางค้า สถานะชาวนา วัด เอกสาร และภาระเกณฑ์แรงงาน สามารถใช้เป็น contextual-play ได้เมื่ออยู่ในขอบเขตที่มีเอกสารรองรับ [1] [2]

เนื้อหารุนแรงต้องรับใช้ผลทางศีลธรรม สถานะ หรือบาดแผลของเรื่อง ไม่ใช้เพื่อทำให้ฉาก “เท่” ความรุนแรงต่อเด็ก การทรมาน และการกดขี่ทางเพศต้องไม่ถูกทำให้เป็น gameplay reward หรือ spectacle หากเรื่องจำเป็นต้องกล่าวถึง ให้ใช้การตัดฉาก ผลตามมา และคำเตือนที่เหมาะสมแทนการบรรยายเพื่อความบันเทิง

| ระดับ fence | ผู้อนุมัติ | รูปแบบที่อนุญาต |
|---|---|---|
| fact-supported | Game Director + content reviewer | ข้อความเฉพาะที่มี fact card/source ตรง |
| contextual-play | Game Director หรือ delegated reviewer | ฉากสมมติที่ใช้โครงสร้างสังคมหรือเทคโนโลยีที่รองรับ |
| campaign-fiction | Game Design owner | NPC, เหตุการณ์ และผลที่แต่งขึ้น โดยติดป้ายชัด |
| insufficient-evidence | AI/Content must stop | ยอมรับว่าไม่ทราบและเสนอทางสมมติที่ไม่อ้าง fact |

## 6. MVP Scope and Change Approval

ทุก feature proposal ต้องตอบให้ครบว่าเพิ่ม value ต่อ player promise ใด, เปลี่ยน state ใด, ต้องแก้เอกสารทีมใด, มีความเสี่ยงประวัติศาสตร์/ภาษา/สิทธิ์หรือไม่, และอะไรคือ test ที่พิสูจน์ว่า feature ทำงาน การไม่ตอบคำถามเหล่านี้ถือว่า proposal ยังไม่พร้อมเข้าสู่ sprint

| ประเภทการเปลี่ยน | อนุมัติโดย | เอกสารที่ต้องแก้ | ตัวอย่าง |
|---|---|---|---|
| เปลี่ยน core loop หรือ outcome | Game Director + Game Design | Shared Master, Game Design, Core source of truth | เพิ่มการใช้ Momentum รอบใหม่ |
| เปลี่ยน state/schema/save | Game Director + Game Development | Shared Master, Development, QA, Release | เพิ่ม resource ใหม่ใน Local Save |
| เปลี่ยน narrative policy/language | Game Director | Shared Master, Game Director, Art/Audio | เพิ่มระดับภาษา NPC ใหม่ |
| เปลี่ยน UI disclosure/CTA | UI/UX lead + Game Director | UI/UX, QA | ซ่อน/แสดงผลทอยในหน้าฉาก |
| เพิ่ม asset/audio | Art lead + Game Director | Art/Audio, Release | เพิ่มเสียง cue หลัง decisive success |

## 7. Operating Cadence for the Director

ก่อนเริ่ม sprint ให้ทบทวน player promise, MVP boundary, open decision และ risk register ระหว่าง sprint ให้ตรวจต้นแบบโดยถาม “ผู้เล่นเข้าใจการตัดสินใจหลักหรือไม่” ไม่ใช่เพียง “หน้าจอสวยหรือไม่” ก่อนปิด sprint ให้ตรวจ state provenance, historical fence, language register, accessibility impact และ QA evidence ทุกสองสัปดาห์ควรมี narrative review ที่สุ่มอ่านฉากจริงจาก AI GM และ Local Trial เพื่อเช็กว่าความยาว รอยผล และน้ำเสียงไม่เสื่อมลง

## 8. Definition of Done สำหรับทีม Game Director

งานเชิงทิศทางเสร็จเมื่อคำตอบของทีมถูกแปลงเป็น acceptance criteria ที่ตรวจได้ ไม่ใช่เพียง mood board หรือความเห็นส่วนตัว งาน narrative เสร็จเมื่อมี fence, language register, agency check และ consequence path งาน scope เสร็จเมื่อมีสิ่งที่ “ไม่ทำตอนนี้” ระบุชัด งานอนุมัติ feature เสร็จเมื่อเจ้าของ implementation, test และ release impact ยอมรับร่วมกัน
